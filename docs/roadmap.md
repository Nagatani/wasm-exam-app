## 3. 共通基盤（採点の柔軟性・スケール）

- ~~**judge が実質 Java 専用**~~ 一部✅（2026-09-11）。CLAUDE.md の「language-agnostic だから設定変更で済む」という記述は誤りだったと判明（`Judge.java` の compile は JVM 内蔵 javac API を直呼びしており Java 専用。実際は新しいコンパイル/実行経路の実装が必要だった）。C の実行経路を追加し、**テストケース修正後の再採点用途にのみ**使用（2-3節）。判明した副産物：
  - **tmpfs は Docker既定で `noexec`** — ネイティブバイナリを書いた `/work` から直接 `exec` できず、`docker-compose.yml` の `/work` tmpfs に `exec` オプションを追加して解決（実機ビルドで発見、コード読みだけでは気づけなかった）。
  - ~~**judge コンテナの外向きネットワーク遮断は未対応のまま**~~ ✅（2026-09-11）。`judge` に `internal: true` を付けると **Docker Desktop（macOS の開発機）でホスト→コンテナの公開ポートが死ぬ**ことを実機で確認したため、`server` を公開ポート経由で `judge` に到達させる開発構成のままでは遮断できなかった。回避策として `server` 自体もコンテナ化し、`judge` と同じ Docker 内部ネットワークに同居させ（サービス名DNSで到達）、`judge` には公開ポートを一切持たせない構成（`docker-compose.prod.yml`）を追加。「ホスト公開ポート方式が Docker Desktop で壊れる」ことが原因であり Docker のフレーバーやホスト OS に依存しないため、Linux 限定にする必要はなかった。DNS 解決・生 IP 接続の両方の遮断とコンテナ間到達性を実機で検証済み。詳細は [`docs/operations.md`](./operations.md) 「デプロイ手順（方法B：コンテナ化した運用構成）」。
  - **本採点（生徒の「実行」／最終提出）をサーバー実行に寄せるか**、**JS/TS/Python まで広げるか**は、いずれも 2026-09-11 の協議で「まずは C ＋再採点専用に絞る」と決定し、意図的に見送り。公平性を上げたい・再採点対象を増やしたいという具体的な必要が出たら再検討。
- **同時実行制御が単一プロセス前提のセマフォ**（`executionQueue.ts`）。`server` を多重化すると効かない。クラス一斉受験で `server` を1本に固定するか、キューを外出し（Redis 等）するかを [`operations.md`](./operations.md) で明言。
- **バックアップが手動 `pg_dump`**。個人情報を持つので、自動スナップショット＋リストア手順を明記。
- **Node 22.11 のネイティブバインディング問題**が残存（`build`/`lint` が `MODULE_NOT_FOUND` で落ちる）。`package.json` の `engines` と CI で 22.12+ を強制。

## 5. 提出モデル（✅ 実装済み — 2026-09-10）

> 旧: 「設問ごとの送信＝1回きり・不可逆・自動で次の問題へ」「受験は 1 回のみ」。下記の決定事項どおりに置き換え済み。実装の詳細は [`CLAUDE.md`](../CLAUDE.md) の「Student exam-taking flow」「Attempt lifecycle, drafts & final submission」、利用手順は [`teacher-guide.md`](./teacher-guide.md) を参照。マイグレーション `20260910120000_add_attempt_lifecycle` の適用が必要。

### 決定事項（すべて反映済み）

1. **設問ごとの「送信」は確定ではなく下書き**。各設問の送信はその受験（attempt）内の下書き保存として扱い、締切または試験全体の「最終提出」まで何度でも上書き・編集できる。設問間の移動も自由（自動遷移をやめる）。
2. **試験全体に「最終提出」を用意し、これを以て評価**する。最終提出時に全設問の下書きをまとめて採点し、その受験の成績を確定する。
3. **受験可能回数は教師が試験ごとに設定**。既定は **1 回**、**無制限**も選択可（任意の N 回も可）。
4. **複数回受験の場合、最後に評価された受験の点数がその試験の最終評価**（最高点ではなく最新）。確定していない受験中の下書きは点数を持たず、直前の確定評価を置き換えない。

### これに伴う変更（設計スケッチ）

- **`Exam`**: `maxAttempts` を追加（`1` 既定 / `null` = 無制限 / 正の整数 = 上限）。教師の試験編集画面に「受験可能回数」フィールド。
- **`ExamAttempt` を単一行から受験ごとの行へ**:
  - `attemptNumber` / `status`（`IN_PROGRESS` \| `SUBMITTED`）/ `submittedAt?` / `score?` を追加。
  - `@@unique([examId, studentId])` → `@@unique([examId, studentId, attemptNumber])`。
  - カウントダウン（`timeLimitMinutes`）は attempt ごとに `startedAt` から計測。新しい受験を始めるとタイマーも最初から。
  - 新しい受験の開始は `maxAttempts` と「直前の受験が `SUBMITTED` 済みか」でガード。
- **下書きの保存先**: 受験中の設問コード＋エディタメトリクスを attempt に紐づけて保存する。案は 2 つ —
  - (a) `Submission` に `attemptId` を持たせ、`draft` / `finalized` を状態で区別（メトリクス列を再利用できる）。
  - (b) `TaskDraft` を別モデルにし、`Submission` は確定分だけの不変レコードに保つ（責務が分離してクリーン）。
  - → 1-1 の autosave はこの下書き保存そのもの。
- **採点タイミング**: 「実行」は従来どおり即時プレビュー。設問「送信」は下書き保存＋（任意で）プレビュー採点。**権威ある採点は最終提出時**に全設問まとめて再実行する。
- **確定レコードの不変性**: 最終提出した受験は不変。`Submission`（確定分）は受験 1 回につき 1 セット。受験中の下書きのみ可変。
- **成績ダッシュボード / CSV**: 集計を「設問ごとの最新提出」→「その生徒の `SUBMITTED` 受験のうち `attemptNumber` が最大のもの」に変更。過去の受験は履歴として保持し、既定は最新のみ表示＋ドリルダウンで全受験を確認できるようにする。
- **「差し戻し」との整理**: 全消去（差し戻し）と「もう 1 回受けさせる」（受験回数の個別付与）を別操作として分ける。
- **画面**: `StudentTaskPage` の設問送信は「下書き保存」に。`StudentExamFinishedPage` を「最終提出の確認（各設問の下書き状態一覧）→ 提出 → 結果表示」の画面へ拡張。

### 残る小さな決定事項

- **締切時に未提出の受験の扱い**: 時間切れ時点の下書きを自動的に最終提出扱いにして評価するか、未評価のままにするか（現行 UI は時間切れ後も送信可）。→ **自動確定を推奨**。
- **無制限受験時の下書きの持ち越し**: 新しい受験は白紙開始か、前回の最終提出コードをテンプレートとして引き継ぐか。
- **受験中に前回評価を見せるか**: 2 回目以降の受験画面で前回の点数・正誤を表示するか（練習用途なら表示、試験用途なら隠す。試験ごとの設定にする手もある）。
