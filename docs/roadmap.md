# 残タスクと今後の展望

未対応の課題と、意図的に対象外としたものの一覧です。ここにあるものは「やる」と決まったものではなく、着手する前に都度判断します。

優先度の目安 — **中**：運用を続けるうちに効いてくる／**低**：必要が具体的になったら。

## 未対応の課題

| 優先度 | 領域 | 項目 | 現状と対応案 |
|---|---|---|---|
| 中 | AI | AIヒントの内容が答えに近づきすぎる | 小型モデル（3B）の限界として確認済みで、プロンプトの調整では解決しなかった。現在は講師が問題ごとに公開する段階数を制限して対処している。プロンプトを変えて「直った」と判断する場合は、実際のモデルで同じ種類のバグに対するヒントを確認すること |
| 低 | AI | AI 機能の実機での確認 | CSP を `enforce` にした状態での WebLLM の動作と、AI作問サポートで生成した Java の解答例を judge で実行して期待値を求める流れ（judge 側はテスト済み）は、実際のモデルでは未確認 |
| 低 | AI | 講師と生徒が同じブラウザを使う場合のモデルキャッシュ | AI作問サポートと AIヒントは同じモデルのキャッシュを共有するため、どちらの設定画面から削除しても両方に効く（許容している制約） |
| 低 | 運用 | `server` の複数インスタンス化 | judge の同時実行制御（`executionQueue.ts`）・採点キュー（`grading.ts`）・ログイン試行の記録（`loginRateLimit.ts`）がプロセスのメモリ上にある。多重化するなら Redis などへの置き換えが必要。現在は単一インスタンスでの運用を前提としている |
| 低 | 運用 | ブラウザ側の実行環境の配信の強化 | Service Worker による事前キャッシュ、clang の学内ミラー（Wasmer レジストリからの取得のため URL を差し替えられない） |
| 低 | 開発 | `main` のブランチ保護 | CI は動いているが、通過をマージの条件にしていない。GitHub のリポジトリ設定で CI のジョブを必須チェックにする（リポジトリ管理者の作業） |
| 低 | 講師 | 試験ごとの担当教員による編集権限 | 現在はどの教員も全試験を編集できる（意図的）。問題バンクの公開／非公開も検索に載るかどうかだけを制御している |

## 意図的に対象外としたもの

再び提案する場合は、改めて判断します。

- **ブラウザ内での Java 実行** — CheerpJ が Java 17 までしか対応しておらず、講義で使う Java 25 の機能（JEP 512）が使えないため、Java はサーバー（judge）で実行している。CheerpJ などが Java 21 以降に対応したら再検討する。
- **外部 BaaS（Firebase / Supabase など）への認証・データの移行** — 個人情報を学内で管理するインフラに置く方針のため。
- **judge のランナーを常駐させて使い回す高速化** — Python の採点はさらに速くなるが、生徒のコードが他の生徒の採点に影響できるようになるため採用しない。提出ごとに新しいプロセスで実行している。
- **演習モード**：サーバー側の下書き保存（ブラウザ内の一時保存で代替）、生徒向けの演習横断の問題検索、ランキング・コンテスト機能。
- **受験回数が複数ある場合の前回コードの引き継ぎ** — 新しい回は白紙（初期テンプレート）から始める。
- **受験中に前回の評価を見せること** — 再受験中は前回の点数を表示しない。
