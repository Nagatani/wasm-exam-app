## 3. 共通基盤（採点の柔軟性・スケール）

- ~~**judge が実質 Java 専用**~~ 一部✅（2026-09-11）。CLAUDE.md の「language-agnostic だから設定変更で済む」という記述は誤りだったと判明（`Judge.java` の compile は JVM 内蔵 javac API を直呼びしており Java 専用。実際は新しいコンパイル/実行経路の実装が必要だった）。C の実行経路を追加し、**テストケース修正後の再採点用途にのみ**使用（2-3節）。判明した副産物：
  - **tmpfs は Docker既定で `noexec`** — ネイティブバイナリを書いた `/work` から直接 `exec` できず、`docker-compose.yml` の `/work` tmpfs に `exec` オプションを追加して解決（実機ビルドで発見、コード読みだけでは気づけなかった）。
  - ~~**judge コンテナの外向きネットワーク遮断は未対応のまま**~~ ✅（2026-09-11）。`judge` に `internal: true` を付けると **Docker Desktop（macOS の開発機）でホスト→コンテナの公開ポートが死ぬ**ことを実機で確認したため、`server` を公開ポート経由で `judge` に到達させる開発構成のままでは遮断できなかった。回避策として `server` 自体もコンテナ化し、`judge` と同じ Docker 内部ネットワークに同居させ（サービス名DNSで到達）、`judge` には公開ポートを一切持たせない構成（`docker-compose.prod.yml`）を追加。「ホスト公開ポート方式が Docker Desktop で壊れる」ことが原因であり Docker のフレーバーやホスト OS に依存しないため、Linux 限定にする必要はなかった。DNS 解決・生 IP 接続の両方の遮断とコンテナ間到達性を実機で検証済み。詳細は [`docs/operations.md`](./operations.md) 「デプロイ手順（方法B：コンテナ化した運用構成）」。

## 5. 提出モデル（✅ 実装済み — 2026-09-10）

> 旧: 「設問ごとの送信＝1回きり・不可逆・自動で次の問題へ」「受験は 1 回のみ」。下記の決定事項どおりに置き換え済み。実装の詳細は [`CLAUDE.md`](../CLAUDE.md) の「Student exam-taking flow」「Attempt lifecycle, drafts & final submission」、利用手順は [`teacher-guide.md`](./teacher-guide.md) を参照。マイグレーション `20260910120000_add_attempt_lifecycle` の適用が必要。

### 決定事項（すべて反映済み）

1. **設問ごとの「送信」は確定ではなく下書き**。各設問の送信はその受験（attempt）内の下書き保存として扱い、締切または試験全体の「最終提出」まで何度でも上書き・編集できる。設問間の移動も自由（自動遷移をやめる）。
2. **試験全体に「最終提出」を用意し、これを以て評価**する。最終提出時に全設問の下書きをまとめて採点し、その受験の成績を確定する。
3. **受験可能回数は教師が試験ごとに設定**。既定は **1 回**、**無制限**も選択可（任意の N 回も可）。
4. **複数回受験の場合、最後に評価された受験の点数がその試験の最終評価**（最高点ではなく最新）。確定していない受験中の下書きは点数を持たず、直前の確定評価を置き換えない。

### これに伴う変更（設計スケッチ）

- **`Exam`**: `maxAttempts` を追加（`1` 既定 / `null` = 無制限 / 正の整数 = 上限）。教師の試験編集画面に「受験可能回数」フィールド。
- **`ExamAttempt` を単一行から受験ごとの行へ**:
  - `attemptNumber` / `status`（`IN_PROGRESS` \| `SUBMITTED`）/ `submittedAt?` / `score?` を追加。
  - `@@unique([examId, studentId])` → `@@unique([examId, studentId, attemptNumber])`。
  - カウントダウン（`timeLimitMinutes`）は attempt ごとに `startedAt` から計測。新しい受験を始めるとタイマーも最初から。
  - 新しい受験の開始は `maxAttempts` と「直前の受験が `SUBMITTED` 済みか」でガード。
- **下書きの保存先**: 受験中の設問コード＋エディタメトリクスを attempt に紐づけて保存する。案は 2 つ —
  - (a) `Submission` に `attemptId` を持たせ、`draft` / `finalized` を状態で区別（メトリクス列を再利用できる）。
  - (b) `TaskDraft` を別モデルにし、`Submission` は確定分だけの不変レコードに保つ（責務が分離してクリーン）。
  - → 1-1 の autosave はこの下書き保存そのもの。
- **採点タイミング**: 「実行」は従来どおり即時プレビュー。設問「送信」は下書き保存＋（任意で）プレビュー採点。**権威ある採点は最終提出時**に全設問まとめて再実行する。
- **確定レコードの不変性**: 最終提出した受験は不変。`Submission`（確定分）は受験 1 回につき 1 セット。受験中の下書きのみ可変。
- **成績ダッシュボード / CSV**: 集計を「設問ごとの最新提出」→「その生徒の `SUBMITTED` 受験のうち `attemptNumber` が最大のもの」に変更。過去の受験は履歴として保持し、既定は最新のみ表示＋ドリルダウンで全受験を確認できるようにする。
- **「差し戻し」との整理**: 全消去（差し戻し）と「もう 1 回受けさせる」（受験回数の個別付与）を別操作として分ける。
- **画面**: `StudentTaskPage` の設問送信は「下書き保存」に。`StudentExamFinishedPage` を「最終提出の確認（各設問の下書き状態一覧）→ 提出 → 結果表示」の画面へ拡張。

### 残る小さな決定事項

- ~~**締切時に未提出の受験の扱い**~~ ✅ 自動確定を採用・実装済み（`maybeSettleAttempt`、詳細は [`CLAUDE.md`](../CLAUDE.md) 「Attempt lifecycle, drafts & final submission」）。
- ~~**無制限受験時の下書きの持ち越し**~~ ✅（2026-09-15、ユーザー確認）**白紙開始を維持**（新しい受験の下書きは attempt ごとに独立しており、既定で初期テンプレートから始まる現行挙動が意図した設計と確認）。前回コードの引き継ぎは非対応のまま。
- ~~**受験中に前回評価を見せるか**~~ ✅（2026-09-15、ユーザー確認）**隠す**。ただし確認の過程で `GET /api/student/exams` の `latestScore` が `hasInProgress` に関わらず常に返っており、生徒ダッシュボードの「・前回: X点」が再受験中も表示されたままになる実装漏れを発見・修正（`hasInProgress` の間は `latestScore: null` を返すよう変更。再受験を提出すると新しい点数が通常どおり表示される）。`StudentExamFinishedPage` 側は元々安全（受験中は `getSubmitPayload` が先に成功するため review モードになり、`result`（前回結果）を取得しない）。

## 7. AI作問サポート（✅ 実装済み — 2026-09-16）

教師から「問題の作問サポート機能」の要望。実現方式（外部LLM API／サーバー自己ホストLLM／ブラウザ内蔵LLM）を提示したところ「ブラウザ内蔵LLM」を選択、加えて「教師ごとに有効/無効を選択式に」「容量使用・削除方法の注意書きを併設」という条件が付いた。

### 方針・設計判断

- **ライブラリ・モデル**: `@mlc-ai/web-llm`（WebGPU、`CreateWebWorkerMLCEngine`）。既定モデルは `Qwen2.5-Coder-3B-Instruct-q4f16_1-MLC`（約2.5GB、コード生成向けの日本語対応小型モデル）に固定、モデル選択UIは作らない。サーバー側の変更・新規APIは一切なし（モデル重みはCDNから取得— Pyodideが既にjsDelivrから取得しているのと同じ「匿名アセット取得」で、生徒の個人情報が絡む話ではない）。
- **有効/無効は「教師ごと」ではなく「このブラウザごと」**（`src/ai/aiAssistSettings.ts`、`localStorage`。`ThemeContext`と同じ発想）。ダウンロードしたモデル本体がそのブラウザにしか存在せず他デバイスに同期しようがないため、サーバー側のアカウント設定にする意味が薄いという判断。
- **期待される出力をLLMに書かせない**: 問題文・初期テンプレート・テストケースの**入力値**・解答例コードのみLLMに生成させ、期待される出力は生成された解答例コードを実際に実行して求める。C/JS/TS/Pythonは既存の`runClientSide()`（`src/runner/clientRunner.ts`）を再利用（`SolutionCheckPanel`の「解答例でテストケースを検証」と同じ発想の再利用）。Javaは自動検証を行わず（既存の`check-solution`エンドポイントがDB保存済みテストケース前提で下書きには使えないため）、期待される出力は空欄で追加し「⚠️自動検証非対応」と明示。
- **バンドルサイズ**: `@mlc-ai/web-llm`はライブラリ単体で数MB（モデル重み抜き）あり、素朴に静的importすると`UserDrawer`（全ページで表示）経由で生徒ページも含めた共通バンドルに混入することが実機ビルドで判明。`React.lazy` + `Suspense`で`AiAssistSettings`（ドロワーを実際に開くまで取得しない）・`AiAssistPanel`（有効化済みと分かってから取得）を分離し、生徒・未使用の教師には一切ロードさせない。

### 実装

- `src/ai/aiAssist.ts`: モデルのロード状態管理（`idle`/`loading`/`ready`/`error`）、`generateTaskDraft()`（JSON mode制約付き生成）、`estimateStorageUsageBytes()`、`clearAiAssistCache()`（`deleteModelAllInfoInCache`）、`isWebGpuSupported()`。
- `src/ai/aiAssist.worker.ts`: `WebWorkerMLCEngineHandler`を動かすESモジュールWorker（既存のC/JS/Python用Workerと異なり`{type:'module'}`が必要）。
- `src/components/AiAssistSettings.tsx`: 教師専用セクション（当初は`UserDrawer`内、2026-09-26 に設定画面 `/settings` へ移動）。トグルON時に容量目安・ブラウザ限定である旨の注意文を表示してから実行、有効時は保存領域使用量の概算表示と`ConfirmDialog`経由の削除ボタン。
- `src/components/AiAssistPanel.tsx`: `TaskEditorPage`の「解答言語」直後に配置。プロンプト＋テストケース数→生成→プレビュー（テストケース件数、Java注記）→「この内容を反映する」。反映は既存の保存経路をそのまま使う（統計文・初期テンプレートは基本情報フォームの未保存state、テストケースは`bulkCreateTestCases`で実際に作成、解答例は`SolutionEditor`に未保存の上書きとして流し込み — 新しい永続化の仕組みは何も作っていない）。
- `TaskEditorPage`側で`isAiAssistEnabled()`を見て有効時のみ`AiAssistPanel`を`lazy`ロード、既存フィールドに内容がある場合は上書き前に確認。

## 8. 演習モード + AIヒント（✅ 実装済み — 2026-09-18/19）

「AOJ（会津大学オンラインジャッジ）のような学習支援を作れないか」という相談から着手。外部LLM API／サーバー自己ホストLLM／ブラウザ内蔵LLMの選択肢を提示したAI作問サポートのときと同様、まず**演習モードそのものの規模感**を協議した結果、AOJ完全互換（多言語コンパイラ拡張・提出履歴・ランキング・コンテスト機能）は今回のスコープ外とし、**「テストではなく学習支援としての、時間制限なし・何度でも提出できるモード」**に絞って着手。加えて「ブラウザローカルLLMによるヒント機能」も要望に上がり、AI作問サポートと同じ`@mlc-ai/web-llm`基盤で追加した。

### 演習モード：設計判断

- **新モデルを作らず`Exam.mode`（`EXAM`/`PRACTICE`）を追加** — 既存の`Task`/`TestCase`/問題バンク/教師オーサリングUIを完全に無改修で使い回せることを優先（詳細は`CLAUDE.md`「演習モード」節）。
- 提出は`PracticeSubmission`という別モデルで、既存の`Submission`/`ExamAttempt`/成績ダッシュボードとは完全に独立（無制限提出が成績集計ロジックを壊さないようにするため）。
- **実装中に見つけた不具合**: 最初の実装では生徒の試験一覧APIが`mode`を見ておらず、演習モードの試験が通常の試験一覧にも表示されてしまっていた（実際にブラウザで操作して発見）。該当する6箇所のクエリすべてに`mode: 'EXAM'`フィルタを追加して修正。

### AIヒント：設計判断と実機検証で分かったこと

- ヒントは3段階固定（着眼点→疑わしい箇所→修正方針）で合意。段階を増やす／無制限に質問できる形にする案も検討したが、**実機検証でヒント3がすでに答えに近づきすぎる傾向が分かった**ため、さらに踏み込む段階を追加するのは見送り、代わりに**教師が問題ごとに公開する段階数の上限（1〜3）を設定できる**形にした。
- **実際にオフバイワンバグ（`for`ループの継続条件を1つ間違えたコード）で検証**: プロンプトを「コード・擬似コードを一切書かない」よう強く制約し、コード検出時は自動で1回再試行するガードも入れたが、**単純な1行バグに対してはヒント3が依然として修正後のコードそのものを書こうとする挙動が残った**（複数回の実機検証で再現）。これは3Bという小型モデルの能力的な限界に近いと判断し、プロンプト調整だけで完全に解決しようとするのではなく、教師が段階数を制限できる仕組みを本命の対策とした。詳細な実測ログは`CLAUDE.md`「AIヒント」節。

### 検証（実機）

演習モード: API（curl）でexam作成・task作成・下書きなし提出・複数回提出の履歴蓄積・既存の試験モードへの影響がないことを確認。ブラウザで生徒ダッシュボードの「演習」セクション表示→演習セット→実行→提出→履歴の一連の操作を確認（上記のモード漏洩バグはこの過程で発見）。

AIヒント: 教師がタスクごとにON/OFF・最大段階を設定→生徒がブラウザでオプトイン（初回ダウンロードあり）→段階ゲート（1回目の不正解までヒント1が押せない、以降順に開放）をブラウザで確認。プロンプト調整の前後で同じバグに対する実際のヒント出力を比較し、上記の結論に至った。テストアカウント・データは都度削除済み。

### 対象外（今回は見送り）

演習モードのサーバー側下書き保存（コードはページ離脱で失われる）、教師向けの演習提出統計・正答率ダッシュボード、生徒向けのタスクバンク横断検索、ランキング・コンテスト機能、AIヒントの段階数を動的に増減させる仕組み。いずれも需要が具体化したら再検討。
