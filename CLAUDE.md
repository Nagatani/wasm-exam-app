## What this is

A browser-based online coding exam/judge system (LMS) for a programming course. Each task is answered in exactly one language, chosen by its author (`task.language`); the student has no language picker. Supported: **C** (client-side, WASI/Wasmer), **JavaScript / TypeScript** (client-side, Web Worker; TS type-stripped with sucrase), **Python** (client-side, Pyodide in a Web Worker), and **Java** (server-side, sandboxed `judge` Docker container — it couldn't be done in-browser, see below). Only Java sends source to the server for execution. Teachers author exams, tasks, and test cases and review student results.

**Java-in-browser is on hold; Java runs server-side instead**: the course teaches Java 25 and wants JEP 512 ("Compact Source Files and Instance Main Methods") — previewed as JEP 495 in JDK 24 — available to students, but CheerpJ's latest shipped release (4.3, April 2026) only supports Java up to 17, a platform ceiling in CheerpJ itself. So (2026-09-09, user sign-off) Java was added as a **server-side** judge: JDK 24 + `--enable-preview`, compiled and run inside the `judge` container, never on the host. Don't build an *in-browser* Java path until CheerpJ (or an alternative) ships Java 21+/25 — check `https://cheerpj.com/docs/changelog.html` first. See "Server-side Java judge" below.

Personal data (student IDs, names, scores) must stay on infrastructure the institution controls — this is *why* the backend is a self-hosted Node/Express + PostgreSQL server rather than a third-party BaaS (Firebase/Supabase were explicitly ruled out for this reason; don't suggest moving auth/data to an external cloud provider without raising this constraint first).

The original single-file mock prototype (`index.html` + `app.js`, a fake `mockWasmRun` that just summed two integers) has been moved to `legacy/` for reference and superseded by the app under `src/` + `server/`.

Being built in explicit phases (see project memory / prior conversation for the full roadmap): Phase 1 (auth + roles), Phase 2 (teacher exam/task/test-case authoring), Phase 3 (Monaco Editor + in-browser C compile/run sandbox — C only), Phase 4 (student exam-taking UI + judge wired into a real submission flow), and Phase 5 (teacher grade dashboard + CSV export) are done, along with post-Phase-5 follow-ups: client-reported editor-integrity metrics on `Submission` (`keystrokeCount` / `pasteCount` / `pastedCharCount`), `ExamAttempt`-anchored exam timing, and the per-student "差し戻し" reset.

**The attempt/draft submission model (Phase 6 lead item, 2026-09-10) is done** — per-task "送信" is gone; a per-task action is now "下書き保存" (a mutable `TaskDraft` per attempt), and the exam has one **final submit** that grades every drafted task into immutable `Submission` rows. Exams carry `maxAttempts` (teacher-set: 1 default / `null` = unlimited); a student's grade is the score of their **latest SUBMITTED attempt** (latest, not best). Time-up auto-finalizes the attempt. See "Attempt lifecycle, drafts & final submission" below.

**Most of Phase 6 (hardening) is now done** (see the sections below and `docs/roadmap.md` §1–8 for what shipped). **Every open item — leftover "残:" notes, deliberately deferred work, and gaps found in the 2026-09-25 code/doc audit — is consolidated in [`docs/roadmap.md`](./docs/roadmap.md) §9** (open items only; §9-0 summarizes the 中-priority ones, §9-7 lists deliberate non-goals, §9-8 what the audit's follow-ups already closed: login rate limiting, closable signup, teacher password reset, the 4 test layers, CI). Check there first when looking for what to do next. Don't jump ahead to a later phase's code without the user's sign-off.

**Multi-language work (separate track from the phases above, 2026-09-09):** adding more answer languages. All three increments are done: Increment 1 (per-task single language: `Task.language` + `Task.starterCode`, teacher picks it, no student picker), Increment 2 (the server-side Java `judge`), Increment 3 (client-side JS / TS / Python runners — `Language` enum gained `JS`/`TS`/`PYTHON` in migration `20260909030000_add_client_languages`). C/JS/TS/Python all run in the browser for the day-to-day exam flow; Java is server-side. **Correction (2026-09-11): the judge executor was *not* language-agnostic** — `Judge.java`'s compile step called `ToolProvider.getSystemJavaCompiler()` (the JVM's own in-process javac API), which is inherently Java-only. Adding C required a real second compile/run path, not a config change — see "Server-side judge (Java + C)" below for what that turned out to involve. (Historical note: Increment 1 briefly shipped a multi-language `allowedLanguages[]` + `task_starter_codes` child table; migration `20260909020000_task_single_language` collapsed it back to one language per task.)

**Practice mode + AI hints (separate track from the phases above, 2026-09-18/19):** a second, untimed learning-support flow alongside the timed exam flow above, plus a teacher-optional AI hint feature scoped to it. Both are done and verified against a real running server/DB/browser. See "演習モード (Practice Mode)" and "AIヒント" below for the full writeup — summary: `Exam.mode` (`EXAM` default / `PRACTICE`) reuses the entire existing `Exam`/`Task`/`TestCase`/teacher-authoring stack for a second flow that has no `ExamAttempt`, no time limit, and unlimited re-submission (`PracticeSubmission`, a new append-only history table, deliberately kept separate from the exam flow's `Submission`/`ExamAttempt`/grade dashboard); the AI hint feature is a 3-stage, teacher-capped, browser-local-LLM hint panel available only on `PRACTICE`-mode tasks, built on the same `@mlc-ai/web-llm` infrastructure as AI作問サポート (below). **A real bug was found and fixed by actually testing in a browser, not by code review**: the first cut of the student-facing exam-listing/attempt routes didn't filter by `mode`, so a `PRACTICE` exam leaked into the timed-exam list with a broken "制限時間: 分" display — see "演習モード" below for the fix. **A real prompt-safety limitation was found by actually running the hint generation against a real bug, not by reasoning about the prompt**: stage 3 hints reliably reveal the literal fix for a simple single-line bug even after several rounds of prompt tightening — see "AIヒント" below; this is why `Task.aiHintMaxStage` (a teacher-set cap) exists as a policy-level mitigation rather than relying on the prompt alone.

The frontend has its own vitest setup (see the root `npm test` above).

**Local Postgres port note**: `docker-compose.yml` maps the container's 5432 to **host port 5433**, not 5432, because this machine already runs a native Homebrew Postgres listening on `127.0.0.1:5432` / `[::1]:5432` — connecting to `localhost:5432` silently hits that instead of the Docker container and fails with `P1010: User was denied access`. If you ever change this mapping back to `5432:5432`, check `lsof -nP -iTCP:5432 -sTCP:LISTEN` first.

**Node version note** (historical — as of 2026-09-25 the dev machine is on Node 22.23.2 and `npm run build` / `npm run lint` / the server build all succeed without any manual step; both `package.json`s now declare `engines: { node: ">=22.12" }` and CI runs on Node 22): this repo previously ran on Node 22.11.0, but Vite 8 / oxlint declare an engine requirement of `20.19+` or `22.12+`. On this Node version, `npm install` silently skips the platform-specific native binding optional dependencies (`@rolldown/binding-*`, `@oxlint/binding-*`), which makes `build`/`lint` crash with `MODULE_NOT_FOUND` until those exact packages are installed manually (e.g. `npm install --no-save @rolldown/binding-darwin-arm64@<version>`). The `server/` package deliberately avoids this class of problem by using pure-JS deps (`bcryptjs`, not native `bcrypt`). Upgrading Node to 22.12+ avoids the frontend issue entirely.

## Architecture

Two independent npm projects in one repo, no shared `node_modules`:

- **Frontend** (repo root): React + Vite + TypeScript + Tailwind CSS v4 (via `@tailwindcss/vite`, no `tailwind.config.js` needed). Routing is `react-router-dom`. Talks to the backend only through `src/api/*` (plain `fetch` wrappers, `credentials: 'include'` so the session cookie rides along) — there is no ORM/DB access from the frontend.
- **`server/`**: Express + TypeScript + Prisma + PostgreSQL. Owns all persistence and all auth. Deployed and run independently of the frontend (e.g. behind a reverse proxy on institution-controlled infra).

There is no third-party BaaS anywhere in this stack. **C** judging happens in the student's browser (WASI/Wasmer); **Java** judging happens in the self-hosted `judge` Docker container (still institution-controlled infra — see "Server-side Java judge"). The `server/` process itself does auth, data storage, authoring/grading APIs, and orchestrating the judge — it never compiles or runs student code in-process.

### Consolidated serving: one process instead of two terminals

For actual day-to-day operation (not active development), `server/src/index.ts` also serves the frontend's production build itself via `express.static`, plus a catch-all `app.get('*', ...)` that falls back to `index.html` so React Router's client-side routes survive a hard refresh. This was added specifically because running two separate dev-server terminals (frontend + backend) every time was operational friction the user didn't want during regular use (e.g. running this during a class).

- `CLIENT_DIST_PATH` (server env, optional) resolves to `path.resolve(__dirname, '../../dist')` by default — this works unchanged whether the server is running via `tsx watch src/index.ts` (dev) or compiled `node dist/index.js` (prod), because `server/src` and `server/dist` sit at the same depth under `server/`, one level below the repo-root `dist/` the frontend builds into. Don't "fix" this path assuming it's dev-only; it's intentionally depth-symmetric.
- The Express routes register the API (`/api/*`) *before* `express.static`/the catch-all, so API paths always resolve first — the static/catch-all block only sees requests nothing else matched.
- **Build the frontend with `VITE_API_BASE_URL` empty** (`.env.production`, copy from `.env.production.example`) when targeting consolidated serving, so `src/api/client.ts`'s `apiFetch` produces same-origin relative paths (`fetch("/api/...")`) instead of a hardcoded dev URL — this is what makes the same build work regardless of what host/port the operational deployment actually runs on. `npm run build` picks `.env.production` over `.env` automatically because Vite defaults to production mode for builds; `npm run dev` still uses `.env` (pointing at `http://localhost:4000`) since it defaults to development mode. Verified by grepping the built bundle for the dev URL (absent) and for a bare `/api/...` path (present) after a `.env.production`-driven build.
- The COOP/COEP headers Phase 3's C sandbox needs (see below) are now set as global Express middleware (`app.ts`, alongside `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin` since 2026-09-26 — asserted by an integration test; no CSP yet, it needs an allow-list for Monaco/Pyodide/WebLLM/Wasmer), not just in `vite.config.ts` — because this server can be the one serving the HTML document in operational mode, and cross-origin isolation has to come from whatever origin actually serves that document.
- This doesn't replace the two-terminal dev workflow — `npm run dev` (Vite, port 5173) + `server`'s `npm run dev` (port 4000) is still how you'd want to work on the frontend with HMR. Consolidated serving is for running the finished app, not editing it.

### Containerized operational deployment (server + judge, 2026-09-11)

A second way to run "operationally" (alongside host-run `npm start` above, not replacing it): `docker-compose.prod.yml` containerizes `server` itself (`server/Dockerfile`) and puts it on the same Docker network as `judge`, so `judge` can be `internal: true` (no outbound network access) without needing a host-published port at all. This exists specifically because `judge` compiles/runs untrusted student code and its egress was never actually blocked (see "Server-side judge" below) — fixing that with host-run `server` doesn't work: `server` would need a host-published port on `judge` to reach it, and a compose network can't be both `internal: true` and have a working host-published port **on Docker Desktop** (verified empirically 2026-09-11 — connection refused; unverified whether plain Linux Docker Engine has the same limit, but the fix here sidesteps the question entirely rather than depending on it).

- **Topology**: `server` is dual-homed — an `internal: true` network shared only with `judge` (reached by service-name DNS, `http://judge:8080`, no published port), and a normal `public` network for its own published port (`4000:4000`, for a reverse proxy) and outbound calls (to the production database, which is external/managed — this compose file has no `db` service on purpose, matching the existing "production should use managed PostgreSQL" guidance). `judge` sits *only* on `internal`.
- **Verified empirically** (not just reasoned about — see the session that added this): a container on `internal: true` can still be reached by name from another container on the *same* internal network (this is what makes `server`→`judge` work); the same container has zero outbound route, confirmed via both DNS resolution failure and a raw-IP connection attempt failing with "Network is unreachable"; a dual-homed container's published port and its access to the outside world both work normally through its *other*, non-internal network membership.
- **`server/Dockerfile`** is a 3-stage build: (1) frontend build on `node:22.12-slim` (glibc, not Alpine — chosen for this stage specifically because Vite/oxlint's native optional deps, per the Node-version note above, are more reliably available for glibc than musl), `VITE_API_BASE_URL=""` baked in exactly like the host-run consolidated-serving build; (2) server build on `node:22.12-alpine`; (3) runtime, also Alpine, production-only deps (`npm ci --omit=dev`, so devDependencies like `tsx`/`typescript`/the `prisma` CLI never reach the image). **Gotcha**: `prisma generate` must run *before* `tsc` in stage 2 — `server/src/**/*.ts` imports types from `@prisma/client`, so building first fails with "has no exported member" for every model/enum (hit and fixed while building this the first time). The runtime image deliberately reproduces the repo's own directory depth (`/app/dist` for the frontend build, `/app/server/dist` for the compiled server) so `CLIENT_DIST_PATH`'s depth-symmetric default resolution (see above) needs no code change to keep working inside the container.
- Config lives in `server/.env.prod.docker` (gitignored; copy from `server/.env.prod.docker.example`), passed to the `server` service via `env_file:` — a separate file from `server/.env` (host-run dev/`npm start`) since the values differ (e.g. `DATABASE_URL` points at a real external host here, not `localhost`/`5433`). `JUDGE_URL` is force-set by `docker-compose.prod.yml` itself (`http://judge:8080`) and overrides anything in the env file, so there's nothing to keep in sync.
- `docker-compose.yml` (dev) and `docker-compose.prod.yml` are **deliberately separate, self-contained files**, not a base+override pair — the two topologies (judge's network membership, whether `server` runs in Docker at all) differ enough that merge semantics for removing/replacing keys like `ports:` weren't worth the risk for a security-relevant setting. Don't run both against the same project directory at once (same implicit Compose project name → `judge` gets fought over).
- `npm run docker:prod` (root `package.json`) is `docker compose -f docker-compose.prod.yml up -d --build`. `.dockerignore` (repo root) keeps `server/Dockerfile`'s build context (the repo root, since it needs both `src/` and `server/`) from sending `node_modules`/`.git`/etc.
- See `docs/operations.md` "デプロイ手順（方法B：コンテナ化した運用構成）" for the operator-facing walkthrough, including how this changes DB-migration and log-viewing commands.

### Database backup / restore (2026-09-14)

`server/scripts/` has two script pairs, both writing/reading `wasm-exam-<timestamp>.dump` (pg_dump custom format) under `server/backups/` (gitignored — dumps carry the same personal data the DB does) with `BACKUP_RETENTION_DAYS`-based pruning (default 30, `0` disables it):

- `backup-db.sh` / `restore-db.sh` — host `pg_dump`/`pg_restore` against `DATABASE_URL` (env or `server/.env`). For a managed/external production PostgreSQL, or any DB reachable from wherever these run.
- `backup-db-docker.sh` / `restore-db-docker.sh` — same, but via `docker compose exec db pg_dump/pg_restore` against `docker-compose.yml`'s dev `db` service, so the client always matches the container's exact PostgreSQL version. **This exists because of a real version-mismatch failure hit while adding these scripts**: this repo pins `postgres:16`, but a Homebrew-installed `pg_dump` 14 on the host could neither write a dump the 16 server would accept (`server version mismatch`) nor read a dump the 16 server produced (`unsupported version in file header`) — running both inside the container sidesteps the question entirely. Must be invoked from the repo root (where `docker-compose.yml` lives) — Compose resolves its project by the *current directory's* name, so running from elsewhere (e.g. a different git worktree, matching the `docker-compose.yml`/`docker-compose.prod.yml` "same project directory" gotcha noted above) reports `service "db" is not running` even though the container is up; pass `COMPOSE_PROJECT_NAME` explicitly to target it from anywhere else.
- Both `backup-*.sh` scripts clean up their own output file if the underlying dump command fails partway (the shell redirect / `pg_dump --file` creates the file before the command can error, so a naive version leaves a misleading 0-byte "backup" behind — hit and fixed while testing this).
- **Verified end-to-end** (not just written): `backup-db-docker.sh` against the real dev DB → `restore-db-docker.sh` into a disposable scratch database (never the real one) → exact row-count match on `exams`/`tasks`/`users`/`submissions` between source and restored DB (note: `pg_stat_user_tables.n_live_tup` is a stale autovacuum estimate, not a live count — don't use it to verify a restore; compare real `SELECT COUNT(*)`s instead, which is what this check actually did). Scratch DB dropped afterward.
- See `docs/operations.md` "バックアップ・リストア" for the operator-facing walkthrough and a cron example.

### Auth: student-ID + password, custom sessions

Login/signup only ever ask for **学籍番号 (student/staff ID) + password** — there is no email concept anywhere in this stack (that was a Firebase-era workaround and no longer applies; `users.studentNumber` is just the primary human-facing identifier now).

- `server/src/routes/auth.ts`: `POST /api/auth/signup` (bcryptjs-hashes the password, creates the user as `role: STUDENT` — except the very first account ever created, which becomes `role: TEACHER`; see "Bootstrapping the first teacher" below), `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` (returns `mustChangePassword`), `POST /api/auth/change-password` (`{ currentPassword, newPassword }` — verifies current, rehashes, sets `mustChangePassword: false` and NULLs `initialPassword`).
- **Bulk student provisioning** (`server/src/routes/students.ts`, `/api/students`, teacher-only): `POST /bulk` takes a roster `[{ studentNumber, displayName }]` (+ optional `courseId` to enroll them all), creates each missing account with a random ~12-char `initialPassword` (unambiguous alphabet, `generateInitialPassword` in `lib/provisioning.ts`), `mustChangePassword: true`, and returns the generated passwords **once**. Existing `studentNumber`s are left untouched and reported as `skipped`. The teacher can also re-view/print the initial passwords from the course roster until the student changes theirs (`GET /api/courses/:id` includes `initialPassword` per enrolled student). `src/components/ProtectedRoute.tsx` redirects a `mustChangePassword` account to `/change-password` before anything else.
  - **Security note**: storing the initial password in plaintext (`users.initialPassword`) is a deliberate, user-signed-off tradeoff (2026-09-11) so a teacher can print a paper credential slip and re-print it if lost. It exists only on institution-controlled infra, only for the window between provisioning and the student's first password change (which NULLs it), and is only ever returned by teacher-gated course routes. If this becomes unacceptable, switch to the one-time-only pattern (return generated passwords solely in the `POST /bulk` response, no column) and add a "reset password" action instead.
- **Login rate limiting (2026-09-25)**: `server/src/lib/loginRateLimit.ts` — in-memory fixed-window failure counters checked *before* bcrypt in `POST /login`: per (studentNumber, IP) `LOGIN_MAX_FAILURES` (10) and per IP `LOGIN_MAX_FAILURES_PER_IP` (100 — a classroom may share one NAT address), both over `LOGIN_LOCKOUT_MINUTES` (15) → `429` + `Retry-After`, even for the right password. Success clears the per-account counter only. In-process state, so it assumes a single server instance (same as `executionQueue.ts`) and resets on restart; the integration suite's `resetDb()` also calls `resetLoginRateLimit()`. Keys on `req.ip`, so behind a reverse proxy `TRUST_PROXY` (e.g. `1`, applied as Express `trust proxy` in `app.ts`) must be set or every client looks like the proxy.
- **Closing self-signup (2026-09-25)**: `ALLOW_SIGNUP=false` makes `POST /signup` 403 — *except* while the DB has zero users, so the bootstrap teacher (below) still works. `GET /api/auth/signup-status` → `{ signupOpen }` lets `LoginPage` hide the 新規登録 link and `SignupPage` show a closed notice. Default stays `true` (dev, tests); `server/.env.prod.docker.example` sets `false`.
- **Teacher password reset (2026-09-25)**: `POST /api/students/reset-password` (`{ studentNumber }`, teacher-only via `studentsRouter`, STUDENT targets only — 400 for a teacher account) puts the account back in the freshly-provisioned state (new `generateInitialPassword()`, stored in `initialPassword` like `/bulk`, `mustChangePassword: true`), revokes **all** that user's sessions in the same transaction, and clears its login lockout. `CoursesPage`'s roster row has a "パスワード再発行" button (`ConfirmDialog`-gated); the new password then shows as the row's 🔑 like any unchanged initial password. 
- **Teacher force-logout (2026-09-26)**: `POST /api/students/force-logout` (`{ studentNumber }`, same teacher-only / STUDENT-only / 404 rules as reset-password) revokes every live session of that student **without** touching the password → `{ studentNumber, displayName, revoked }`. UI: `AdminPage`'s 強制ログアウト form and a "ログアウトさせる" button on `CoursesPage`'s roster row, both `ConfirmDialog`-gated. This and reset-password are the only places another user's sessions get revoked.
- **Stale-session cleanup (2026-09-26)**: `purgeStaleSessions()` (`server/src/lib/session.ts`) `deleteMany`s every expired *or* revoked session row (a missing row and a dead row both mean "not signed in" to `getUserForSessionToken`, so it's always safe). `startSessionCleanup()` runs it at startup and every `SESSION_CLEANUP_INTERVAL_HOURS` (default 6, `0` disables) on an `unref()`'d timer — called from `index.ts` only, never `createApp()`, so tests don't start timers (the integration test calls `purgeStaleSessions()` directly).
- Sessions are DB-backed (`server/src/lib/session.ts`, `Session` model in `prisma/schema.prisma`), not JWT — a session token is a random 32-byte value; only its SHA-256 hash is stored, so a DB dump can't be replayed as a valid cookie. The token is delivered as an `httpOnly` cookie (`session_token`). This was a deliberate choice over stateless JWT specifically so a session can be revoked immediately (`Session.revoked`) instead of waiting out a token's expiry — relevant for a teacher needing to force-logout a student during an exam in a later phase.
- `server/src/middleware/auth.ts`: `requireAuth` resolves the cookie to a `req.user`; `requireRole('TEACHER')` gates admin-only routes.

### Role assignment is server-side only

A client can never set or escalate its own role:

- Signup creates `role: STUDENT` (`server/src/routes/auth.ts`) for every account **except the very first one ever created**, which becomes `role: TEACHER` (2026-09-16, user decision — see "Bootstrapping the first teacher" below) — there's no request field for role either way, so the caller never chooses it.
- The only way any *other* user becomes `TEACHER` is `POST /api/admin/promote-to-teacher` (`server/src/routes/admin.ts`, `{ targetStudentNumber }`), which requires the *caller* to already have `role: TEACHER` — `AdminPage` (`/teacher/admin`, via the ☰ drawer) has a form for it. `admin.ts` also serves `GET /api/admin/service-health` → `{ db: ok|error, judge: ok|error|disabled }` (`$queryRaw SELECT 1` + `judgeHealthy()`), shown on `AdminPage`.
- There is no Firestore-style security-rules layer here; this invariant is enforced entirely by what the Express routes allow, so don't add a route that lets a user PATCH their own `role`.

**Bootstrapping the first teacher**: `POST /api/auth/signup` runs `prisma.user.count()` and creates the new account as `TEACHER` when it's `0`, `STUDENT` otherwise (`server/src/routes/auth.ts`) — the very first person to sign up on a fresh deployment (expected to be the administrator setting the system up) becomes a teacher automatically, no DB access needed. This check-then-create is deliberately **not** wrapped in a serializable transaction — two signups landing in the same instant before any user exists could both become `TEACHER`, an accepted race since the window only exists for the few seconds between a fresh deploy and the first real signup. If that one-time window is ever missed (e.g. the first account was created before this existed, or got deleted), fall back to promoting directly in the database: `docker exec <postgres-container> psql -U wasm_exam -d wasm_exam -c 'update users set role='"'"'TEACHER'"'"' where "studentNumber"='"'"'<id>'"'"';'` (Prisma model fields are camelCase, so the actual column name needs quoting in raw SQL).

**Program-execution time (2026-09-26)**: each per-test-case result now carries an optional `timeMs` (wall-clock run time) — no migration, since it lives inside the existing `results` JSON. See "Student exam-taking flow" below for how judging then happens without the client ever holding the hidden answer.

### Teacher exam/task/test-case authoring API (Phase 2)

All of `server/src/routes/exams.ts`, `tasks.ts`, `testCases.ts` are mounted at `/api/exams`, `/api/tasks`, `/api/test-cases` and gated by `requireAuth, requireRole('TEACHER')` at the router level (`router.use(...)`) — there is currently no ownership check beyond "is a teacher," i.e. any teacher can edit any other teacher's exam. That's intentional for a small teaching-team admin console, not an oversight; revisit only if the user asks for per-teacher exam isolation.

- `POST/GET /api/exams`, `GET/PATCH/DELETE /api/exams/:examId` — exam CRUD. `GET /:examId` returns a lightweight `tasks` array (id/order/title/points only); full task content (statement, starter code, test cases, solutions) is only ever fetched via `GET /api/tasks/:taskId`, so the exam detail page stays cheap to load.
- `POST /api/exams/:examId/duplicate` (2026-09-16, user request — "試験そのものの一括作成・複製" was called out as the biggest data-entry friction point) copies an entire exam: metadata (title `<title>（コピー）`, description, `timeLimitMinutes`, `maxAttempts`, `courseId`) plus every task in one call, each with the exact same fields `POST /api/tasks/:taskId/duplicate` copies (statement, language, starter, points, comparison settings, tags, test cases, reference solutions). Deliberately resets `status` to `DRAFT` and clears `opensAt`/`closesAt` regardless of the source — a copy should never silently inherit "already published" or a stale schedule. `TeacherDashboard`'s exam list has a per-row "複製" button (`src/api/exams.ts`'s `duplicateExam`).
- `POST /api/exams/:examId/tasks` creates a task (mounted on `examsRouter`, not `tasksRouter`, since it's the nested-create route). `GET/PATCH/DELETE /api/tasks/:taskId` operate directly on a task by id. `language` in the request body is optional (2026-09-16) — when omitted (the normal case: `ExamDetailPage`'s "＋問題を追加" never sends one), it falls back to `exam.defaultLanguage` rather than a hardcoded language.
- `POST /api/tasks/:taskId/test-cases` creates a test case; `POST /api/tasks/:taskId/test-cases/bulk` (`{ cases: [{ input, expectedOutput, isSample }] }`, ≤200) appends many at once; `PATCH/DELETE /api/test-cases/:testCaseId` (separate router, since a test case is addressed directly once created, not through its parent task).
- `GET /api/exams/:examId/publish-check` (teacher-only) — advisory pre-publish lint: `{ issues: [{ level: 'error'|'warn', message }] }` (no tasks, a task with no test cases / no sample / 0 points / empty expected output, a FLOAT-mode task with non-numeric expected output, a Java task while the judge is unconfigured, `closesAt <= opensAt` or already past). Publishing is never blocked; `ExamDetailPage` just renders it above the task list and re-runs it after edits.
- `POST /api/tasks/:taskId/regrade` (teacher-only, **Java or C** — `isRegradeCapable()`) re-runs every existing `Submission` for the task through the judge against its *current* test cases + comparison settings, updates each submission's `overallStatus`/`score`/`results`, and recomputes affected `ExamAttempt.score`s. A sanctioned mutation of otherwise-immutable submissions (like 差し戻し); runs sequentially through `withJudgeSlot`, passing `language: judgeLanguage(task.language)`. Returns `{ regraded, changed, failed }`. `TaskEditorPage` shows a "既存の提出を再採点" button for Java/C tasks. JS/TS/Python still can't be re-graded this way — that's a further judge-extension decision, deliberately deferred (2026-09-11 sign-off: C-only, regrade-only for now — see `docs/roadmap.md` §3).
- `POST /api/tasks/:taskId/duplicate` (`{ examId? }`) copies a task — statement, language, starter, points, comparison settings, **plus its test cases and reference solutions** — into the same exam (or `examId`), appended last, titled `<title>（コピー）`.
- `PUT /api/tasks/:taskId/solutions/:language` upserts a reference-solution row (`language` is `c`/`java`, case-insensitively upper-cased server-side against the `C`/`JAVA` enum); `DELETE` on the same path removes it. Solutions are never returned by any student-facing endpoint — `server/src/routes/student.ts` doesn't touch the `Solution` model at all, keep it that way.
- `PATCH /api/tasks/:taskId` carries `language`, `starterCode`, `comparisonMode` and `floatTolerance` (all plain task fields saved with the task form, not via their own routes). The reference solution still has its own `PUT/DELETE /api/tasks/:taskId/solutions/:language` route.
- Exam `POST /` + `PATCH /:examId` also carry `maxAttempts`, the `opensAt` / `closesAt` scheduling window (Zod `z.coerce.date().nullable()`), `courseId` (`null` = unscope), `defaultLanguage` (2026-09-16, teacher request — omit to keep/default; see "Database schema" above), and `mode` (`EXAM`/`PRACTICE`, 2026-09-18 — omit to keep/default `EXAM`; see "演習モード" below for what this changes). `timeLimitMinutes` is required only when `mode !== 'PRACTICE'` (enforced by `examInputSchema`'s `.superRefine`, not the DB). `POST /:examId/duplicate` copies it to the new exam alongside `maxAttempts`/`courseId`/`mode`.
- `server/src/routes/courses.ts`, mounted at `/api/courses`, teacher-only: CRUD on `Course`; `POST /:courseId/enrollments` bulk-adds *existing* students by `studentNumber` (`{ studentNumbers: string[] }`, ≤1000 → `{ added, alreadyEnrolled, notFound }` — the roster paste/CSV import feeds this); `DELETE /:courseId/enrollments/:userId` unenrolls. To create *new* accounts use `POST /api/students/bulk` (above), which can also enroll them via its `courseId`. `getExamResults` lists a course-scoped exam against its enrollees instead of every `STUDENT`; `student.ts` filters `GET /exams` and 404s `GET /exams/:examId` / `POST .../attempts` / `GET /tasks/:taskId` for a non-enrolled student (`examVisible(courseId, enrolledCourseIds)`).
- `POST /api/tasks/:taskId/check-solution` (teacher-only authoring aid) — runs a candidate solution `{ code }` (optionally `{ code, inputs: string[] }` to run against ad-hoc stdin values instead — used by AI作問サポート for Java drafts) against every test case and returns `{ compileFailed, compileStderr, outcomes: [{ testCaseId, stage, stdout }] }` (the same shape `runClientSide` returns). **Java only** — for C/JS/TS/Python it 400s, because those run in the teacher's browser via `runClientSide`. Never persists. Used by the "解答例でテストケースを検証" panel, whose "実際の出力を期待値にする" button then `PATCH`es that test case's `expectedOutput`.
- Deleting an `Exam` or `Task` cascades to its children via Prisma's `onDelete: Cascade` (see `schema.prisma`) — there's no soft-delete or orphan cleanup needed at the route level.

Frontend: `src/api/exams.ts` + `src/api/tasks.ts` wrap these endpoints; `src/types/exam.ts` holds the corresponding TS shapes. `TeacherDashboard` lists exams + an inline create form (both it and `ExamDetailPage`'s exam-edit form carry a「既定の解答言語」select bound to `Exam.defaultLanguage`, 2026-09-16); `ExamDetailPage` (`/teacher/exams/:examId`) edits exam metadata and lists/creates tasks; `TaskEditorPage` (`/teacher/exams/:examId/tasks/:taskId`) edits statement (Markdown, with 編集 / 分割 / プレビュー view modes — `react-markdown`, no raw-HTML plugin, don't add `rehype-raw` without thinking through XSS from teacher-authored Markdown), a single `language` `<select>`, the starter template (a Monaco editor, all part of the main task form save — when the task has no starter code yet the field is pre-filled from `LANGUAGE_TEMPLATE[task.language]`, and changing the language `<select>` swaps that skeleton in only while `isUntouchedTemplate()` holds, never clobbering code the teacher typed; the pre-fill leaves the form "未保存" so it's persisted on the next save), plus a "一括追加" panel (`BulkTestCasePanel` — `===`-separated cases, `---`-separated input/expected, `@sample` first line; POSTs to `.../test-cases/bulk`; a "ファイルから読み込む" file input (2026-09-15, `.txt`, 2MB cap) reads a file's content into the same textarea via `file.text()` — no separate upload endpoint, it's just a convenience fill for what a teacher would otherwise paste, so the existing review-then-"この内容で追加" step still applies before anything is actually created — this file-load control was extracted into `src/components/FileLoadButton.tsx` on 2026-09-16 so `CoursesPage`'s two roster textareas (below) could reuse it verbatim), `TestCaseRow` per test case (its 時間制限/メモリ制限 inputs only render when `showLimits` — passed as `judgeRelevant` from the parent — is true, i.e. `task.language` is `JAVA` or `C`; other languages ignore these fields entirely so the controls would be misleading there), and one `SolutionEditor` for the task's language with its own independent "解答例を保存" button and a "解答例でテストケースを検証" button (results render in `SolutionCheckPanel` below it; `applyActualAsExpected` PATCHes a test case straight to the produced stdout, and each `TestCaseRow`'s `key` includes its `expectedOutput` so it remounts with fresh field state when that happens). `ExamDetailPage` has a per-row "複製" button (`POST .../duplicate`). Test case fields save independently per-row via their own "このテストケースを保存" button, not as part of the task form submit.

**Task bank: cross-exam search, tagging, public/private sharing, JSON export/import (2026-09-13)**: previously the only way to reuse a task across exams was `duplicate` with an explicit target `examId` — no way to *discover* a task in another exam without already knowing its id. This adds a searchable view instead of a new template model (user sign-off: keep it lightweight — every task ever authored is itself a bank entry, no separate `TaskTemplate` table):

- **Schema**: `Task.tags String[] @default([])` (free-form labels, no separate `Tag` model — a scalar array keeps authoring frictionless; the bank offers autocomplete from tags already in use rather than a managed taxonomy) and `Task.isPublic Boolean @default(false)` (migration `20260913074346_add_task_bank_fields`).
- **Visibility is a discovery boundary, not access control** (explicit user decision — teachers want private-by-default with an opt-in public flag): a task is visible in bank search to the teacher who owns its exam (`exam.createdById`) plus, if `isPublic`, to every other teacher. It does **not** restrict direct task/exam access — that stays the existing "any teacher can edit any exam" admin-console model (see "Teacher exam/task/test-case authoring API" above); a private task opened directly via its exam is unaffected. Don't conflate the two when extending this — tightening direct access would be a separate, bigger decision.
- `GET /api/task-bank` (`server/src/routes/taskBank.ts`, teacher-only) — `?q=` (title substring, case-insensitive), `?language=`, `?tags=a,b` (`hasSome`, i.e. match-any), `?scope=all|mine|public` (default `all` = mine ∪ public). Returns lightweight rows (`title`, `language`, `points`, `tags`, `isPublic`, `testCaseCount`, `examId`/`examTitle`, `ownerName`, `mine`) — never the full statement/test cases/solutions, so browsing stays cheap; opening a result still goes through the normal task editor or `duplicate`. `GET /api/task-bank/tags` returns the distinct tag set across everything the caller can see, for autocomplete.
- **Adding a bank result into an exam reuses the existing `POST /api/tasks/:taskId/duplicate`** (`{ examId }`) unchanged — no new "add" endpoint. `tags`/`isPublic` now travel with the copy like every other task field `duplicate` already copies.
- **Export/import** is a *separate* mechanism from the bank, for moving a task across server instances (a colleague on a different deployment, or a backup) rather than within one shared DB: `GET /api/tasks/:taskId/export` downloads `{ format: 'wasm-exam-task/v1', tasks: [...] }` (`server/src/lib/taskPortable.ts` holds the shared zod schema — always an array, even for one task, so a future bulk/whole-exam export can reuse the envelope without a breaking change); `POST /api/exams/:examId/tasks/import` validates that same shape and creates one task per entry, appended last. **An imported task always arrives `isPublic: false`** regardless of the source file's flag — a teacher opts back into the bank explicitly after reviewing what they just pulled in, not automatically from someone else's export. A `.refine()` on the solutions array rejects a file with two solutions for the same language before it ever reaches Prisma's `@@unique([taskId, language])` (would otherwise 500 partway through creating the task).

### In-browser C compile/run sandbox (Phase 3)

`src/runner/cRunner.ts` wraps `@wasmer/sdk`: `compileAndRunC(sourceCode, stdin)` fetches `clang/clang` from the Wasmer registry (`Wasmer.fromRegistry`, memoized module-wide — only downloaded/initialized once per page load), compiles the source with `clang.entrypoint.run({ args: [...], mount: {...} })`, and if that succeeds, runs the resulting `.wasm` via `Wasmer.fromFile` with `stdin` passed straight through `SpawnOptions`. Returns `{ stage: 'compile_error' | 'runtime_error' | 'success', compileStderr, stdout, stderr, exitCode }`. `runCompiledC(wasmBinary, stdin, timeoutMs = C_TIME_LIMIT_MS)` races the run against a **10s wall-clock timeout** (`Promise.race` on `Instance.wait()`); `@wasmer/sdk`'s `Instance` has no kill API, so on timeout it calls `Instance.free()` and returns `{ timedOut: true }` — the runaway program may keep occupying one worker from the SDK's *bounded* pool until a page reload, but the tab no longer hangs and the judge gets a deterministic outcome (`timedOut` → per-test `tle` → `TLE`, same as a JS/Python/Java timeout — it was originally rolled into `RE`/`WA` before distinct `TLE` verdicts existed). A client-side memory cap (MLE) is still not implemented.

**This needs cross-origin isolation to work at all**: `@wasmer/sdk` uses `SharedArrayBuffer` for its Web Worker thread pool even for single-threaded programs, which browsers only expose when the page sends `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`. `vite.config.ts` sets these for `server`/`preview`; **whatever serves the production build in Phase 5+ deployment must set the same two headers**, or the sandbox will fail silently/mysteriously in production even though it works in dev.

**Performance characteristics to keep in mind**: the `clang/clang` WASIX package is ~106MB (measured via `content-length`), fetched once per browser session and cached by the browser afterward. On a ~256KB/s link that's ~7 minutes for the very first compile; on campus/broadband it'll be much faster, but don't be surprised by a slow first run in any environment — this is inherent to shipping a real clang toolchain to the browser, not a bug. Subsequent runs in the same session reuse the in-memory `Wasmer` instance.

`src/components/CodeEditor.tsx` wraps `@monaco-editor/react`; its `language` prop takes `c`/`java`/`javascript`/`typescript`/`python`/`plaintext` (Monaco registers each as a real language id). It also takes a `markers` prop (`EditorMarker[]`) that it pushes via `monaco.editor.setModelMarkers` — `StudentTaskPage` feeds it `parseCompileErrors(language, stderr)` (`src/lib/compileErrors.ts`, best-effort per-toolchain location parsing) on a CE and clears it on the next edit. Used in `TaskEditorPage` (starter + solution editors, mode = `task.language`), in `StudentTaskPage` (mode = `task.language`), and in `SandboxPage` (`/teacher/sandbox`, teacher-only) — a standalone manual-verification harness kept around independently of the real student flow (see below); don't delete it. `src/lib/language.ts` holds the shared per-language metadata (label, Monaco id, filename) plus `RUNNABLE_LANGUAGES` (everything the app can execute — currently all five) and `SERVER_EXEC_LANGUAGES` (`JAVA` only); `server/src/lib/language.ts` is the server-side counterpart (`LANGUAGES`, `languageSchema`, `parseLanguageParam`).

### Client-side JS / TS / Python runners (multi-language Increment 3)

`src/runner/clientRunner.ts` is the single entry point for every browser-executed language — `runClientSide(language, source, testCases, onProgress)` dispatches by language and returns the same `{ compileFailed, compileStderr, outcomes[] }` the C path always did (no self-declared verdict). `StudentTaskPage`'s `executeAgainstAllTestCases` just calls it; `prewarmClientRunner(language)` kicks off any heavy download early.

- **JS / TS** — `src/runner/jsRunner.ts` + `js.worker.ts`. `prepareJs()` transpiles TS with **sucrase** (`transforms: ['typescript']` — type-*stripping* only, so a type error never fails the judge; a **syntax** error does) or, for JS, syntax-checks via `new Function()` (V8's SyntaxError has no line/column, so on failure the source is re-parsed with sucrase `transforms: []` purely to append `(line:col)` for the editor marker — V8 stays the authority on validity; 2026-09-26, `jsRunner.test.ts` + an E2E step that filters markers by the `compile-errors` owner, since Monaco's own JS validation adds markers too). Each test case then runs in a throwaway classic Web Worker that's `terminate()`d on a 10s timeout. The worker exposes `readline()` / `read()` for stdin and `print()` / `console.*` / `write()` for stdout (no `process` / `require`); top-level `await` is not supported. `sucrase` is a pure-JS dep (no native bindings — safe on the pinned Node, matching the repo's "pure-JS deps" preference).
- **Python** — `src/runner/pyRunner.ts` + `py.worker.ts`. **Pyodide** (CPython→WASM) loaded once per worker from the jsDelivr CDN by default (~10MB first load, works under the app's COOP/COEP headers). Since 2026-09-26 the location is a build-time setting, `VITE_PYODIDE_BASE_URL` (self-hosted pyodide dist; `resolvePyodideBaseUrl` in `pyRunner.ts`, unit-tested) — resolved on the main thread and sent as `baseUrl` with every worker message, because `py.worker.ts` is a classic worker (`importScripts`) and can't read `import.meta.env`. An E2E spec runs a Python task through the default CDN path. One worker is reused across a run's test cases; on a 15s timeout it's `terminate()`d and recreated. Student code runs via `exec()` in a fresh globals dict with `sys.stdin`/`stdout`/`stderr` redirected; a traceback goes to stderr and marks the test a runtime error.
- All four client languages now cap run time: JS 10s / Python 15s kill and recreate the Web Worker; C 10s abandons the `@wasmer/sdk` instance (see above). An infinite loop can't freeze the tab in any of them. A timeout is reported as a `tle` outcome stage → per-test `TLE` → overall `TLE` (see `judge.ts`). Client-side MLE isn't detected (only Java's judge reports `oom` → `mle` → `MLE`).
- `clientRunner.ts` exposes `getRuntimeReadiness()` (`{ c, python }` each `idle`/`loading`/`ready`/`error`, tracked in `cRunner.ts` / `pyRunner.ts`) and `prewarmAllClientRunners()`. `StudentDashboard` renders a "実行環境の準備状況" card from these and prewarms on mount, so a class can warm the ~106MB clang / ~10MB Pyodide downloads before an exam rather than at the first "実行". See `docs/operations.md` "クライアントランタイムの配信・キャッシュ".
- **Hard-gating exam start on runtime readiness (2026-09-13)**: `GET /api/student/exams` (`server/src/routes/student.ts`) now also returns each exam's `languages` (distinct `Task.language` values across that exam's tasks, from the same `tasks` include already used for `totalPoints` — no extra query). `StudentDashboard` polls `getRuntimeReadiness()` once (shared between the summary card and every row, previously the card ran its own separate `setInterval`) and, for each exam, disables the **受験する / もう一度受験する** button — showing "準備中..." plus a "今すぐ準備する（<言語>）" link that calls `prewarmClientRunner` only for that exam's not-yet-`ready` languages — until every client-exec language the exam actually uses (C / Python; JS/TS/Java always read as ready, needing no warm-up) is ready. This exists specifically to stop a student from starting the countdown and then burning exam minutes on a ~106MB clang / ~10MB Pyodide download that could have happened before clicking start. **Deliberately does not gate 受験を再開する** (resuming an already-`IN_PROGRESS` attempt) — that attempt's clock is already running, so blocking the resume path would only add more wasted time, not less.

**Friendlier failure messages for network / runtime-load problems (2026-09-11)**: previously, a failure to reach `server` at all (`fetch` itself rejecting — offline, DNS, server down) or a failure to download the clang/Pyodide toolchain (registry/CDN unreachable) surfaced the browser's own raw, often-English rejection message (e.g. "Failed to fetch") straight to the student, since every catch site already does `err instanceof ApiError ? err.message : …` or `err instanceof Error ? err.message : …` and just displays it. Server-originated failures (judge down, queue full, language unconfigured) were already friendly Japanese text from `server/src/routes/student.ts` — only these two client-side cases weren't. Fixed at the source instead of per-call-site:
- `src/api/client.ts`'s `apiFetch` now wraps the `fetch()` call itself in try/catch and rethrows a network-layer failure as `ApiError('サーバーに接続できませんでした。…', 0)` (status `0` = no HTTP response at all) — every existing `err instanceof ApiError` catch across the whole app (student *and* teacher pages) gets this for free, no per-page changes needed.
- `cRunner.ts`'s `loadClang()` rethrows a registry/init failure as a friendly "C の実行環境（clang）の読み込みに失敗しました。ページを再読み込みしてから再度お試しください。" — phrased around reloading (not just retrying) because `clangPromise` stays memoized even on rejection (see its own comment), so a same-page retry re-awaits the same failed promise instead of re-fetching.
- `py.worker.ts`'s outer catch already tagged an infrastructure-level failure (as opposed to a student-code compile/runtime error) with `fatal: true`; `pyRunner.ts` now turns that into the same kind of friendly message, and — unlike C — actually resets the worker on a `fatal` reply so the *next* call gets a fresh worker and a real retry (Pyodide's internal load promise can otherwise stay memoized-rejected the same way clang's does). A worker-level `error` event (the worker crashing outright) is now treated the same way.
- These are load/network failures, not verdicts — they still flow through the existing `compileFailed`/outcome shape (e.g. Python surfaces as `compileFailed: true` with this message as `compileStderr`, so it renders in the same "⚠️ コンパイルエラー" panel `StudentTaskPage` already has; it isn't actually a compile error, but restructuring that categorization is a larger change than this fix, deliberately out of scope here).

### Server-side judge: Java (exam flow) + C (regrade only) (multi-language Increment 2 + 2026-09-11)

`judge/` (its own Docker image, `judge` service in `docker-compose.yml`) is a single-file HTTP service (`judge/Judge.java`, uses `com.sun.net.httpserver` + Gson) that compiles and runs student **Java and C** code **inside the container only** — never on the host, so it behaves identically on macOS and Linux. The container *is* the sandbox: `cap_drop: ALL`, `read_only`, tmpfs `/work` (mounted `exec` — see gotcha below) + `/tmp`, `pids_limit`, `mem_limit`, `cpus`, `no-new-privileges`, non-root uid.

- Protocol: `POST /run { language?: 'JAVA'|'C', code, tests: [{ id, stdin, timeLimitMs, memoryLimitMb }] }` → `{ compile: { ok, stderr }, results: [{ id, stdout, stderr, exitCode, timedOut, oom, timeMs }] }` (`timeMs` since 2026-09-26 — rebuild the `judge` image to get it; `judgeClient.ts` treats it as optional). `language` omitted/unrecognised defaults to `JAVA` (`Judge.java`'s `normalizeLanguage`), so every pre-2026-09-11 caller keeps working unchanged. It does **not** compute a verdict — `judgeSubmission()` still does, from these raw outcomes.
- **Java**: `compileJava()` uses `ToolProvider.getSystemJavaCompiler()` (in-process javac API — this is *why* it doesn't generalize to other languages, see the multi-language-track correction above). Per test case it forks `java --enable-preview -cp <classes> Main` (source always written as `Main.java`; entry class always `Main`).
- **C** (added 2026-09-11, scope deliberately narrow — see class doc in `Judge.java`): `compileC()` subprocess-invokes `gcc -O2 -std=c11 -Wall -o a.out main.c -lm` (cwd = srcDir, so diagnostics read `main.c:LINE:COL:` — the same shape @wasmer/sdk's clang produces client-side). **It is wired up for exactly one thing today: the teacher "regrade" endpoint** (`POST /api/tasks/:taskId/regrade`, gated by `isRegradeCapable()` in `server/src/lib/attempts.ts`, a superset of `isServerExec()`) — a student's own C "実行"/final submit still runs entirely in-browser (`isServerExec('C')` stays `false`, unchanged). `oom` is always `false` for C (only a coarse `ulimit -v` guard, no reliable OOM signal to grep unlike Java's `-Xmx`).
- Both languages share the same process-execution harness: per-request tmp dir under `/work`, `sh -c 'ulimit -f …; ulimit -t …; [ulimit -v … for C;] exec "$@"'`, wall-clock `waitFor` + `destroyForcibly` on the process tree, tmp dir deleted in a `finally`.
- **Gotcha if you touch `judge/Dockerfile` or the tmpfs mounts**: Docker mounts tmpfs **`noexec` by default**. Java never hit this (the `java` binary itself lives on the read-only rootfs; only `.class` *data* sits on `/work`), but a freshly-`gcc`-compiled C binary has to be `exec()`d from wherever it was written — `docker-compose.yml`'s `/work` tmpfs entry has `,exec` appended specifically for this (`/tmp` stays `noexec`, nothing needs to run from there). Found by running the actual build (`docker compose build judge` / `up -d judge` + `curl .../run`), not by inspection — verify similarly before trusting any further change here.
- **Network egress from `judge` is NOT blocked in `docker-compose.yml`** (the dev/two-terminal setup) — `cap_drop`/`read_only`/tmpfs don't stop outbound `connect()`, and `judge` needs a host-published port there for a host-run `server` to reach it, which rules out `internal: true` (see below). **It *is* blocked in the containerized operational deployment** (`docker-compose.prod.yml`) — see "Containerized operational deployment" below for how and what was verified.
- `server/src/lib/judgeClient.ts` talks to it over `JUDGE_URL` (default `http://localhost:4001`; empty ⇒ server-exec disabled, student UI shows "準備中" for Java). `server/src/lib/executionQueue.ts` bounds it: a global concurrency cap (`JUDGE_CONCURRENCY`, default 3) plus a per-user in-flight cap of 1 (second concurrent request → 429). The regrade endpoint reuses this same queue/slot.
- `timedOut` → `tle` stage → `TLE`; `oom` → `mle` → `MLE`; a non-zero exit → `runtime_error` → `RE` (rolls into overall `WA`). `judge.ts`'s `computeOverall` reports overall `TLE`/`MLE` only when *every* failing test agrees, otherwise the mix is `WA`.

### Student exam-taking flow + judge (Phase 4)

**The server, never the client, decides AC/WA/CE.** `server/src/lib/judge.ts`'s `judgeSubmission(testCases, points, { compileFailed, outcomes }, comparison?, allowPartialCredit?)` is the *only* place a verdict is computed. `comparison` (`{ mode, floatTolerance }` from the task, default `EXACT`) selects the `compareOutput` rule: `EXACT` (trim whole string, exact match — the original), `TRIM_TRAILING_WS`, `IGNORE_BLANK_LINES`, `FLOAT` (whitespace-tokenised, numeric tokens within `floatTolerance`), or `IGNORE_CASE` (2026-09-14 — same per-line trailing-whitespace/blank-line normalization as `TRIM_TRAILING_WS`, then `.toLowerCase()` on both sides; migration `20260914122155_add_ignore_case_comparison`). `src/lib/compareOutput.ts` is a client mirror used only by the teacher's "検証" panel; both files' switch statements need every mode kept in sync (no shared source between server/client for this one — see the "no shared node_modules" architecture note); `server/test/compareOutput.test.ts` enforces this by running the same case table against both. Where the `{ compileFailed, outcomes }` comes from depends on the language: for **client-exec** languages (C, JS, TS, Python) the browser compiles+runs locally and reports `{ testCaseId, stage: 'success'|'runtime_error', stdout }` per test case (never a self-declared pass/fail); for **server-exec** languages (Java) the browser sends only the source and `server/src/routes/student.ts`'s `resolveOutcomes()` calls the `judge` container and builds the outcomes from its output. Either way the client can only change *what code runs*, not make the server believe output matched a stored `expectedOutput` when it didn't.

**Partial credit (2026-09-12, `Task.allowPartialCredit`)**: `judgeSubmission`'s internal `computeScore()` is the only place that turns per-test-case results into a `score`. The default (`allowPartialCredit: false`) is all-or-nothing — full `points` only on a clean overall `AC`, `0` otherwise, unchanged from before this feature. With the flag on, `score = Math.round(points * passed / results.length)` regardless of `overallStatus` — e.g. 3/4 test cases (sample + hidden alike) passing on a 10-point task scores 8 even though the overall badge still reads WA. A compile failure is still always `0` (the early `if (input.compileFailed)` return in `judgeSubmission` happens before `computeScore` is even reached, so the flag can't affect it — nothing ran). All four `judgeSubmission` call sites (`attempts.ts`'s `maybeSettleAttempt`, `tasks.ts`'s regrade route, `student.ts`'s run-preview and submit-finalize routes) pass `task.allowPartialCredit` through. `TaskEditorPage` exposes it as a "部分点を認める" checkbox next to the comparison-mode fields; `StudentTaskPage`'s run-preview verdict badge now always shows `(score/points点)` next to the status label (previously the preview showed only the AC/WA/... badge, no score) so a partial-credit task's non-AC preview doesn't read as "0点" when it isn't.

**Non-revealing WA hints (2026-09-14)**: covers both roadmap items "非公開テストのWAヒント" and "Presentation Error の区別" without adding a new verdict/status value (deliberately — `SubmissionStatus`/`PerTestCaseStatus` are enum-backed and a new value needs a migration, same reasoning already noted for why a per-test `RE` never got promoted to an overall `SubmissionStatus`). `PerTestCaseResult` gained an optional `hint?: string`, computed by `judge.ts`'s `computeWaHint()` only on an actual output mismatch (never on a missing/RE/TLE/MLE result — those already say why on their own). It tries each *looser* comparison mode in order — `TRIM_TRAILING_WS` → `IGNORE_BLANK_LINES` → `IGNORE_CASE` (skipping whichever mode the task is already using, since that one just failed) — and if one would have matched, reports only that **category** ("行末の空白や改行の違いの可能性があります。" etc.), never the actual expected content or its line count. Only if none of those would match does it fall back to a plain "行数が異なります" structural check — checked *last*, not first, because `IGNORE_BLANK_LINES` can itself change the effective line count, so a raw line-count check up front would misdiagnose a blank-line difference as something else. A genuinely-wrong answer gets no hint at all (`hint` stays `undefined`, which `JSON.stringify` simply omits).
- **Transport is scoped to the live preview on purpose**: only `POST /api/student/tasks/:taskId/run` echoes `PerTestCaseResult[]` (hence `hint`) back to the student — final `submit` and `GET .../result` only ever return a `{ taskId, status, score }` summary, never the full per-test results, so a hint from a *submitted* answer is never re-surfaced to the student after the fact (it's still persisted in `Submission.results` for the teacher's "提出コードと結果を表示" panel, which is fine — that view already shows `expectedOutput` unconditionally for every test case, so a coarse hint adds nothing a teacher doesn't already fully see). `StudentTaskPage` renders it only for a non-sample WA (`!tc.isSample && result?.status === 'WA' && result.hint`) — a sample WA still gets the full `SampleDiff` instead, where a coarse hint would be redundant.
- **Three independent `PerTestCaseResult`-shaped type declarations exist and must be kept in sync by hand** (no shared package between server/frontend): `server/src/lib/judge.ts`, `src/types/student.ts`, and `src/types/exam.ts`'s `SubmissionDetailResult` (teacher-facing). Since 2026-09-26 `server/test/typeParity.test.ts` asserts at compile time (`npm run typecheck:test`, CI) that these three, the overall-status unions, and the frontend `ComparisonMode` / `Language` unions equal their server/Prisma counterparts — adding a field or enum value on one side only now fails the typecheck — this was already true before `hint` existed (same duplication CLAUDE.md's task-bank/comparison-mode notes already call out for `ComparisonMode`), `hint` just adds one more field to keep matched across all three.
- **Verified via the real judge path** (not just unit-level): direct `judgeSubmission()` calls confirmed all four hint categories plus both no-hint cases (a genuinely wrong answer, a clean AC); then a full `POST /api/student/tasks/:taskId/run` round-trip against a real hidden test case confirmed the hint reaches the HTTP response exactly as computed. **Gotcha hit while doing this**: the first verification attempt silently hit a stale server — port 4000 was already held by a *different*, longer-running dev server (the user's own, started from the main checkout, not this worktree — confirmed via `lsof`/`ps` before touching anything) that obviously predates this change, so requests were served by old code with no `hint` field at all. Re-ran the same test against a throwaway instance on `PORT=4100` instead of touching the port-4000 process.

- `server/src/routes/student.ts`, mounted at `/api/student`, gated by `requireAuth` only (not role-restricted — a teacher previewing the student view is fine; every route additionally filters to `exam.status === 'PUBLISHED'`, 404ing otherwise so a draft exam's existence isn't even leaked):
  - `GET /exams` — published exams + per-exam attempt state for the caller: `taskCount` / `totalPoints` / `maxAttempts` / `opensAt` / `closesAt` / `notYetOpen` / `closed` / `attemptsUsed` / `hasInProgress` / `canStart` (false outside the schedule window) / `latestScore` (2026-09-15, user decision: **`null` while `hasInProgress`** — a student mid-retake shouldn't see the prior attempt's score on the dashboard; it reappears once that retake is submitted, reflecting the *new* score, never the hidden old one. Found and fixed a real leak while implementing this: it previously returned unconditionally. `StudentExamFinishedPage`'s result view was already safe on its own — while an attempt is in progress, `getSubmitPayload()`/`GET /exams/:examId/attempt` succeeds first and puts the page in review mode, so it never calls `GET /exams/:examId/result` to begin with).
  - `POST /exams/:examId/attempts` — begin a new attempt (or return the in-progress one; idempotent). 409 if the retake cap is reached, if `now < opensAt`, or if `now >= closesAt`. This is the *only* way an `ExamAttempt` row is created.
  - `GET /exams/:examId` — read-only: task summaries + `maxAttempts` / `opensAt` / `closesAt` / `totalPoints`, the current `attempt` (`{ id, attemptNumber, startedAt, deadline, draftedTaskIds }` or null; `deadline` already clamped to `closesAt`), `attemptsUsed`, `canStartNew`. Never returns a prior attempt's evaluation.
  - `GET /tasks/:taskId` — statement/points/`language`/`starterCode` + hidden-`expectedOutput`-redacted test cases, **plus** the current attempt's saved `draft` for this task (`{ code, keystrokeCount, … }` or null).
  - `PUT /tasks/:taskId/draft` — "下書き保存": upserts the `TaskDraft` for `(current attempt, task)` with `{ code, keystrokeCount, pasteCount, pastedCharCount, timeSpentSeconds }`. Never judged. 409 if no in-progress attempt.
  - `POST /tasks/:taskId/run` — ephemeral preview: judges, never persists. Body carries **no language** (the task fixes it): `resolveOutcomes()` branches on `task.language` — `{ compileFailed, outcomes }` for a client-exec language, `{ code }` for Java. Response `{ verdict, compileStderr }`.
  - `GET /exams/:examId/attempt` — everything the review page needs to grade the in-progress attempt client-side: per task its `language` / `serverExec` / `hasDraft` / `draftCode` / test-case `input`s. 404 if no in-progress attempt; 409 if this call auto-finalized an expired one.
  - `POST /exams/:examId/submit` — **finalize the current attempt.** Body `{ tasks: [{ taskId, compileFailed, outcomes }] }` carries per-task results only for client-exec languages (the browser ran the *saved draft*); Java tasks are compiled+run server-side from their stored draft. For each drafted task it builds a verdict via `judgeSubmission` and writes an immutable `Submission` (code + metrics copied from the draft); undrafted tasks get no submission ("未提出"). Then a guarded `updateMany` flips the attempt to `SUBMITTED` with `score` + `submittedAt` (so a double-submit can't grade twice). Response `{ attempt, perTask }`.
  - `GET /exams/:examId/result` — the latest SUBMITTED attempt: `{ exam:{…,tasks,totalPoints}, attempt:{ attemptNumber, score, submittedAt, startedAt } | null, perTask:[{ taskId, status, score }], attemptsUsed, maxAttempts, canRetake }`. Drives `StudentExamFinishedPage`'s result view.
- **Attempt lifecycle, drafts & final submission** (`server/src/lib/attempts.ts`): `maybeSettleAttempt(id)` auto-finalizes an attempt that is IN_PROGRESS *and* past `attemptDeadline(startedAt, timeLimitMinutes, closesAt?, extraMinutes?)` (= `min(startedAt + (limit+extra), closesAt + extra)`; `extra` from `extraMinutesFor(examId, studentId)` = the `ExamTimeExtension` row) — decision 2026-09-10, "自動確定して評価". It's called opportunistically from every student read and from `getExamResults`. The server can't re-run browser languages, so a drafted client-exec task the student never submitted is graded **WA/0**; Java drafts are still run through the judge. The status flip is a single guarded `updateMany`, so concurrent settles don't double-write. The client also fires the finalize itself at the deadline (`StudentTaskPage` redirects to the review page, which auto-submits) — the server settle is the fallback for a closed browser.
- `Submission.overallStatus` gets `AC`/`WA`/`CE`/`TLE`/`MLE` (all five `SubmissionStatus` enum values are now produced — `judge.ts`'s `computeOverall`). A per-test runtime crash still shows as an `'RE'` badge but rolls into overall `WA`, since `RE` isn't a `SubmissionStatus` value — don't add it without a migration. `Submission.language` is copied from `task.language` server-side (any of `C` / `JAVA` / `JS` / `TS` / `PYTHON`).

**Frontend**: `src/runner/cRunner.ts` is split into `compileC(source)` + `runCompiledC(wasmBinary, stdin)` (`compileAndRunC` kept as a thin `SandboxPage` wrapper) so a run compiles once and executes the same binary against every test case. `StudentTaskPage` (`/student/exams/:examId/tasks/:taskId`) is the 3-column screen (statement + samples / Monaco fixed to `task.language` / run + **下書き保存** buttons + a header "試験を提出する"). "▶ コンパイル＆テスト実行" is the ephemeral preview (`executeAgainstAllTestCases` → `runClientSide` for C/JS/TS/Python, or a source POST for Java). "下書き保存" PUTs the draft — no navigation, no judging, no auto-advance. A failing sample test case renders a line-by-line `SampleDiff` (expected vs. actual, trailing-whitespace made visible, a line-count-mismatch note); TLE/MLE/RE samples show the partial output with a short reason instead. Editor content is seeded from the saved draft (falls back to `starterCode`), and the editor-metric counters are seeded from the draft too so revisiting a task continues rather than resets. If there's no in-progress attempt the page redirects to `/finished`; at the deadline it redirects there too. `StudentExamFinishedPage` (`/student/exams/:examId/finished`) is now three-mode: **review** (in-progress attempt — lists per-task draft status, "最終提出する" runs every client-exec draft locally then `POST /submit`, auto-submits if past the deadline), **result** (latest SUBMITTED attempt + total + "もう一度受験する" when `canRetake`), or loading. `StudentDashboard` shows per-exam attempt state and the right action (受験する / 受験を再開する / もう一度受験する / 結果を見る). Submissions are immutable; a student re-takes via a fresh attempt (within `maxAttempts`), and the teacher's per-student "差し戻し" still wipes everything (see Phase 5). Both editor pages use `useUnsavedGuard` for a `beforeunload` warning; `StudentTaskPage` also auto-saves the draft before in-app navigation away from a task.

**Unsaved-code backup in `localStorage` (2026-09-26)**: `src/lib/localBackup.ts` + `src/hooks/useCodeBackup.ts` keep a browser-local copy of editor code that isn't saved server-side yet — `StudentTaskPage` (edits since the last 下書き保存, key `exam:<userId>:<attemptId>:<taskId>`) and `PracticeTaskPage` (edits since load/last submit, key `practice:<userId>:<taskId>`; practice has no server draft at all). Written debounced (500ms) while dirty, removed when clean. After a crash/reload, a stored copy that differs from what the page loaded becomes `pending` and `RestoreBackupBanner` offers 復元する / 破棄する; restoring only fills the editor (the exam still needs 下書き保存). Removed explicitly after a successful `persistDraft`, for the whole attempt after final submit (`StudentExamFinishedPage`, whose review table also flags "保存していない編集あり" per task), for everything on logout (`UserDrawer`, so the next person on a shared PC can't read it), and on read once older than 24h. Keys include the user id so another account on the same browser never sees it. **Gotcha (found in the browser, fixed)**: the check-for-backup and the write/clear effect must not both run for a new key in the same commit — the clear branch (`!dirty`) would delete the backup the banner is about to offer, so a second reload lost it. `useCodeBackup` keeps `{ key, pending }` in one state and only runs the write effect once `checked.key === key`, and never touches storage while a backup is pending.

**Testing gotcha worth knowing before writing more browser-driven checks against Monaco pages**: `page.keyboard.type()` to drive Monaco is unreliable — its auto-indent and auto-close-bracket features corrupt raw keystroke simulation (observed firsthand: typing `#include <stdio.h>` character-by-character came out as `#io.h>` with compounding indentation on each line, producing a real compile error that had nothing to do with the app). Set content via `page.evaluate(() => window.monaco.editor.getModels()[0].setValue(code))` instead — it still flows through the same `onDidChangeModelContent` → React `onChange` path a real edit would, just without the corruption.

### Teacher grade dashboard + CSV export (Phase 5)

`server/src/lib/examResults.ts`'s `getExamResults(examId)` is the single source of truth shared by both the JSON dashboard endpoint and the CSV export, specifically so the two can never disagree — always add new result fields there, not separately in each route. It lists **every `STUDENT` user**, not just ones who touched this exam. A student's grade is their **latest SUBMITTED attempt** (highest `attemptNumber`, not best score); the row's per-task cells, `totalScore`, `elapsedSeconds` and `attemptCount` all come from that attempt and its `Submission`s (one per task). It first calls `maybeSettleAttempt` on any IN_PROGRESS attempt past its deadline so an auto-finalized result shows rather than "未提出".

- `GET /api/exams/:examId/results` (`examsRouter`, teacher-only like the rest of that router) — `{ exam, tasks, students: [{ id, studentNumber, displayName, results: [{ taskId, status, score, submittedAt, keystrokeCount, pasteCount, pastedCharCount, timeSpentSeconds }], totalScore, lastSubmittedAt, startedAt, elapsedSeconds, attemptCount, extraMinutes }] }`. `status` is `null` for a task the latest attempt didn't submit — the frontend renders "未提出", don't conflate it with a real WA. Every per-cell metric field is `null` there too. `elapsedSeconds` / `startedAt` are `null` until the student has a SUBMITTED attempt; `attemptCount` is the number of SUBMITTED attempts.
- `GET /api/exams/:examId/results/csv` — same data. Summary columns first (`学籍番号,氏名,試験名,<task titles…>,合計点,受験回数,提出日時,所要時間（秒）`), then per-task detail appended at the tail: one `<task>（解答時間・秒）` block, then one `<task>（打鍵数）` block. Two things worth knowing if you touch this: (1) the body is prefixed with a UTF-8 BOM (`server/src/lib/csv.ts`'s `UTF8_BOM`) because Excel misdetects encoding on Japanese CSVs without one; (2) `Content-Disposition` sends **both** an ASCII `filename=` and an RFC 5987 `filename*=UTF-8''...`.
- `GET /api/exams/:examId/students/:studentId/submission-detail[?attempt=N]` — the student's **latest SUBMITTED attempt** by default, or SUBMITTED attempt `N` (404 if it doesn't exist or is still in progress — past-attempt drill-down, 2026-09-26), as `{ attemptNumber, latestAttemptNumber, attempts: [{ attemptNumber, score, startedAt, submittedAt }] (every SUBMITTED attempt, asc), tasks: [{ taskId, title, order, points, language, submitted, overallStatus, score, code, keystrokeCount, pasteCount, pastedCharCount, timeSpentSeconds, results, testCases }] }` — the submitted source plus per-test-case `input` / `expectedOutput` / `actualOutput` / `status` so a teacher can see *why* a verdict landed. `ExamResultsPage`'s expanded row loads this lazily behind a "提出コードと結果を表示" button (`SubmissionDetailView`), which shows a "受験回" button row (★ = the graded latest attempt) when there are 2+ submitted attempts and refetches with `?attempt=N` on click.
- `PUT /api/exams/:examId/students/:studentId/time-extension` (`{ extraMinutes }`, 0 removes) — upserts the per-student `ExamTimeExtension`. `getExamResults` returns each row's `extraMinutes`; `ExamResultsPage` has an inline per-student "延長（分）" input.
- `PUT /api/exams/:examId/students/:studentId/extra-attempts` (`{ extraAttempts }` 0–100, 0 removes; 400 on an unlimited-attempts exam; 2026-09-26) — upserts the per-student `ExamAttemptGrant`. Every student route that checks or reports `maxAttempts` (`GET /exams`, `POST .../attempts`, `GET /exams/:examId`, `GET .../result`) uses `effectiveMaxAttempts(exam.maxAttempts, extra)`, so the student sees their own cap. `getExamResults` returns `exam.maxAttempts` and each row's `extraAttempts`; `ExamResultsPage` has a "追加受験" column (a shared `NumberSettingCell`, same as 延長) and shows the 受験 column as `used / cap`.
- `DELETE /api/exams/:examId/students/:studentId/results` — the "差し戻し" reset. In one `$transaction` it `deleteMany`s every `Submission` **and** every `ExamAttempt` for that (exam, student) pair (`TaskDraft`s cascade from the attempt delete), putting them back to never-took-it. This is the *only* sanctioned break in submission immutability — teacher-only, irreversible, confirmed in the UI. It is distinct from a student simply re-taking within `maxAttempts`.
- Frontend: `src/api/exams.ts`'s `downloadExamResultsCsv(examId)` does its own `fetch` (the response isn't JSON), reads a `Blob`, triggers a download via a temporary `<a download>`. `ExamResultsPage` (`/teacher/exams/:examId/results`, linked from `ExamDetailPage`'s "成績を見る") renders a table with client-side search, a submitted / not-submitted filter, sortable columns (score / elapsed / name / last-submitted), a non-sortable 受験 (attempt count) column, a per-row 延長 (time-extension) number input, summary stat tiles, per-task AC-rate bars, an expandable per-student row (per-task status, score, 打鍵数, 解答時間, 📋 paste-count badge), a lazily-loaded "提出コードと結果を表示" panel (submitted code + input/expected/actual/status per test case), and the per-row "差し戻し" button.

### 演習モード (Practice Mode): untimed, unlimited-retry learning support (2026-09-18)

A second, parallel flow to the timed exam flow above: no `ExamAttempt`, no time limit, no retake cap, unlimited re-submission — for learning support rather than assessment. Scoped down from a full AOJ-style rewrite after discussion (see project memory) to "reuse everything reusable, only add what's genuinely new."

**Design decision: `Exam.mode` (`ExamMode`: `EXAM` default / `PRACTICE`), not a new model.** A practice "problem set" is just an `Exam` with `mode: PRACTICE` — this was chosen specifically so the entire existing `Task`/`TestCase`/`Solution`/task-bank/teacher-authoring UI (`ExamDetailPage`, `TaskEditorPage`, `TestCaseRow`, `BulkTestCasePanel`, `SolutionEditor`, `TaskBankPicker`, duplicate/export/import) works **completely unmodified** for authoring practice content — a new parallel model would have meant rebuilding all of that. The tradeoff this accepts: `Exam.timeLimitMinutes` is now `Int?` (nullable, required only for `mode: EXAM`, enforced at the Zod layer via `examInputSchema`'s `.superRefine` in `server/src/routes/exams.ts` — the base object was split into `examInputBaseSchema` specifically because `.superRefine()` returns a `ZodEffects` that can't itself call `.partial()`, which the PATCH route needs); `maxAttempts`/`opensAt`/`closesAt` stay as-is (already nullable/optional) and are simply ignored for `PRACTICE`. `GET /api/exams/:examId/publish-check` skips the `opensAt`/`closesAt` window checks when `mode !== 'EXAM'`. `mode` propagates through `POST /:examId/duplicate` and task-copy/import like every other exam field.

**Submissions: a new `PracticeSubmission` model, deliberately not `submissions` with a nullable examId** — see the `practice_submissions` schema entry above for why (unlimited resubmission would corrupt the exam grade dashboard/CSV/差し戻し, which all assume a `Submission` row belongs to one graded `ExamAttempt`). No `ExamAttempt`/`TaskDraft` exists for practice mode at all — code lives only in the browser tab's React state while the student has the page open (**no server-side draft persistence** — an explicit, accepted scope cut; since 2026-09-26 a browser-local `localStorage` backup survives a reload, see "Unsaved-code backup" above).

**Backend**:
- `server/src/lib/execution.ts` (new) — `resolveOutcomes()`/`RunRequestError`/`MAX_CODE_LENGTH`/`outcomeSchema`/`clientExecSchema`/`serverExecSchema`, extracted out of `server/src/routes/student.ts` so both the exam flow and practice flow share one client-exec-vs-Java dispatch implementation instead of two copies drifting apart. Behavior is unchanged from what `student.ts` always did.
- `server/src/routes/practice.ts` (new), mounted at `/api/student/practice` in `index.ts` (registered *before* `/api/student` — doesn't strictly matter since the two path prefixes never collide, Express falls through to the next matching mount either way, but keeps the more specific prefix visually first). `requireAuth` only, no role gate, same as `student.ts`:
  - `GET /exams` — `PUBLISHED` + `mode: 'PRACTICE'` exams visible to the caller (same `enrolledCourseIds`/`examVisible` course-scoping helper `student.ts` uses) → `{ id, title, description, courseId, defaultLanguage, taskCount, totalPoints, languages }`. No attempt-shaped fields (`attemptsUsed`/`canStart`/`latestScore`) — those don't mean anything here.
  - `GET /exams/:examId` — task list summary for one practice set (`id/order/title/points/language`) + `totalPoints`.
  - `GET /tasks/:taskId` — statement + hidden-test-redacted test cases (same `expectedOutput: tc.isSample ? tc.expectedOutput : undefined` rule as `student.ts`) + `aiHintEnabled`/`aiHintMaxStage` (see "AIヒント" below).
  - `POST /tasks/:taskId/run` — ephemeral preview via the shared `resolveOutcomes()` + `judgeSubmission()`, never persists. Same semantics as the exam flow's `POST /api/student/tasks/:taskId/run`, just without needing an `ExamAttempt` to exist first.
  - `POST /tasks/:taskId/submit` — judges the same way, then creates a `PracticeSubmission` row (never overwrites a previous one — unlimited history). The request body always includes `code` — for a client-exec language this rides alongside `{ compileFailed, outcomes }` purely so the code can be persisted (`execution.ts`'s Zod schemas don't require it and ignore the extra field when resolving the verdict); for Java it's the same `{ code }` the exam flow already sends.
  - `GET /tasks/:taskId/submissions` — the caller's **own** `PracticeSubmission` history for that task, `submittedAt desc`, full code + results included (a teacher-review-detail-shaped response, but student-facing and self-scoped — this is the "AOJ-style see your own past submissions" affordance).

### AIヒント: 演習モード限定の段階的AIヒント機能 (2026-09-19)

A teacher-optional, per-task, 3-stage AI hint panel available **only** on `PRACTICE`-mode tasks (`StudentTaskPage`/the exam flow never renders it, regardless of the flag). Built on the same in-browser `@mlc-ai/web-llm` infrastructure as AI作問サポート above — reuses `loadAiAssistModel()` from `src/ai/aiAssist.ts` directly, so opting into hints never triggers a second model download if the model's already cached (and vice versa for a teacher who's also used AI作問サポート on the same browser).

**Design, agreed with the user up front**: a fixed 3-stage sequence — ヒント1 着眼点 (approach-level nudge) → ヒント2 疑わしい箇所 (points at a suspicious area, no fix content) → ヒント3 修正方針 (explains the fix direction) — unlocked one at a time, ヒント1 only becomes pressable once the student has an actual non-AC run result (never before they've tried anything themselves). Considered and rejected: more than 3 fixed stages, or an open-ended "ask again" round count — see the real-model findings below for why pushing further specificity didn't look safe. What shipped instead: `Task.aiHintMaxStage` (1-3, teacher-set per task) caps how many of the 3 stages are ever exposed, so a teacher can restrict a task to ヒント1/2 only without the model itself needing to behave any differently.

**`src/ai/aiHint.ts`** (model calls) + **`src/ai/aiHintContext.ts`** (the pure, web-llm-free half — types, `buildStageContext`, `looksLikeCode`; split out 2026-09-25 so it's unit-tested in `aiHintContext.test.ts`; `aiHint.ts` re-exports the types/labels):
- `HintStage = 1 | 2 | 3`, `HINT_STAGE_LABEL`, `HintContext { language, statementMarkdown, code, verdict, compileStderr }`.
- `buildStageContext(stage, ctx)` — what the model is allowed to see, growing by stage. Stage 1 gets only the overall verdict status label (WA/CE/TLE/MLE), nothing else. Stage 2/3 add: the compile error text (if CE), and per test case — for a **sample** (`isSample`), the full input + actual output (safe: the student already sees this in the statement panel); for a **hidden** test, only its status and the existing non-revealing `hint` string (`judge.ts`'s `computeWaHint()`, the same one shown to the student for a non-sample WA elsewhere) — never `expectedOutput`, which the client never has for a hidden test case anyway (nothing to redact, just nothing requested).
- `STAGE_INSTRUCTION[stage]` (per-stage wording) + a blanket `NO_CODE_RULE` appended to *every* stage's system prompt (forbids code/pseudocode/specific conditional expressions outright — see the tuning history below for why the blanket rule replaced an earlier "1 line of pseudocode is OK at stage 3" exception). `temperature: 0.4` (lower than `aiAssist.ts`'s draft-generation `0.7` — a hint should be a fairly literal application of the stage instruction, less sampling variance means fewer chances to wander into forbidden territory).
- `looksLikeCode(text)` / `CODE_LIKE_PATTERN` — a regex safety net (`for\s*\(`, `while\s*\(`, `if\s*\(`, `[{};]`, `==`, `!=`, `<=`, `>=`, `++`, `--`, `scanf(`, `printf(`, `` ``` ``) checked against the model's output; a match rejects the response rather than showing it. Deliberately over-inclusive — a false positive just costs a retry, which is cheap here.
- `generateHint()` retries internally (`MAX_ATTEMPTS = 2`) when `looksLikeCode` rejects, escalating the system prompt each retry (`buildRetryNudge()` tells the model its previous answer was rejected for containing code and to explain again using zero code syntax). Not a fixed model/network-error retry — a `GENERATE_FAILURE_MESSAGE` (engine/network failure) is rethrown immediately, unretried.
- **Real-model testing findings (2026-09-19) — read before touching this prompt again**: tested against an intentionally seeded off-by-one bug (`for (int i = 0; i < n - 1; i++)` instead of `i < n` in a "sum of N integers" task) by actually running the full flow in a browser with the real downloaded model, repeatedly, not by reasoning about the prompt text.
  - **First pass** (temp 0.6, stage 3 allowed "a line of pseudocode"): stage 1 said outright that the code "fails to read the last integer" — already too specific for an abstract hint. Stage 2 was appropriately vague. **Stage 3 wrote the corrected `for` condition verbatim** — the literal fix, not a "direction."
  - **After tuning** (`NO_CODE_RULE` blanket ban replacing the stage-3 pseudocode exception, temp 0.4, stage 1 instruction strengthened to also forbid *naming* the specific mechanism): retested the same bug. Stage 1 still named "forループの範囲外" — better, but still more specific than intended, and not caught by the regex guard because it's prose, not code syntax. Stage 2 said the code "doesn't confirm the last `scanf` reads `n-1`" and told the student to "修正してください" — highly revealing in plain language, again not code syntax so the guard didn't catch it. **Stage 3 hit the code-detection guard on repeated real attempts** (observed rejecting 4 consecutive real generations in one test run, before `MAX_ATTEMPTS` was turned down from 4 to 2 specifically because those retries essentially never succeeded for this class of bug and just made the student wait longer for a failure).
  - **Conclusion, written down so this isn't re-litigated with the same approach**: this reads as a capability ceiling of the 3B model, not a prompt-engineering gap that more wordsmithing fixes. For a single-line fix, "describe the direction of the fix" and "state the fix" are the same content — there's no wording that reliably keeps a small model on the abstract side of that line. The regex guard and retry reduce *literal code* leakage but do **not** stop the model from being extremely specific in prose (see the stage 1/2 examples above), and don't guarantee stage 3 ever succeeds for a simple bug (it may exhaust its retries and just show `CONTAINS_CODE_MESSAGE`, which is the accepted worst case, not a bug).
  - This is *why* `Task.aiHintMaxStage` exists: the mitigation that actually works is a teacher-level policy decision (don't expose ヒント3 on a task where this matters), not a stronger prompt. Don't claim a prompt change "fixes" this without re-running the same kind of real-browser, real-model test above first — a plausible-sounding tightened instruction is exactly what produced the "after tuning" pass above, and it still wasn't reliable.

**Student opt-in — deliberately separate from the teacher's AI作問サポート flag**: `src/ai/aiHintSettings.ts` (own `localStorage` key `wasm-exam-ai-hint-enabled`, own change event), not a reuse of `aiAssistSettings.ts`'s flag — reusing it would mean a teacher opting into AI作問サポート on some browser silently also turns on the student hint feature for anyone who later logs in as a student on that same browser (or vice versa): two different features, opted into by two different roles, for two different reasons, that happen to share the same underlying downloaded model/cache. `src/components/AiHintSettings.tsx` mirrors `AiAssistSettings.tsx`'s structure (caution-before-enabling → download → storage-usage caption → `ConfirmDialog`-gated cache deletion) but imports the enable/disable functions from `aiHintSettings.ts` and reuses `aiAssistModelSizeLabel()`/`estimateStorageUsageBytes()`/`clearAiAssistCache()`/`isWebGpuSupported()` from `aiAssist.ts` unchanged (same cache, so clearing it from either settings panel affects both features — an accepted edge case, only relevant if the same physical browser is used by both a teacher and a student). `SettingsPage` lazy-loads `AiHintSettings` for a `STUDENT`, the mirror image of `AiAssistSettings` for a `TEACHER`.

**`src/components/HintPanel.tsx`** — the 3-button UI, lazy-loaded from `PracticeTaskPage.tsx` and only mounted once both `task.aiHintEnabled` (teacher) and `isAiHintEnabled()` (student's browser opt-in) are true. `visibleStages = STAGES.filter(s => s <= task.aiHintMaxStage)` — a stage beyond the teacher's cap is never rendered, not just disabled. Stage 1's button is disabled until `verdict !== null && verdict.overallStatus !== 'AC'`; stage *n* (n>1) is disabled until stage *n-1* has been generated. A generated hint's text is kept once shown (not regenerated as the student keeps editing — pressing a stage again isn't a thing once it's revealed); `key={task.id}` on the panel remounts it fresh (all stages re-locked) when the student switches tasks.

**Verified**: schema/migrations apply cleanly; API round-trips for `aiHintEnabled`/`aiHintMaxStage` create/PATCH/duplicate/export/import/student-facing-GET all confirmed via curl; out-of-range `aiHintMaxStage` (e.g. `5`) 400s. Real browser: teacher enables the flag + sets max stage on a task, with the `HelpPopover` explanations rendering correctly (see "Setting-item explanations" above); student opts in via the drawer and the panel appears reactively without a reload; stage-gating confirmed live (all three buttons disabled before any run, ヒント1 enables after a real WA, ヒント2/3 stay locked until unlocked in order); a task with `aiHintEnabled: false`, and a student who hasn't opted in, both correctly show no panel at all, even with the model already cached from other testing. The prompt-tuning findings above came from actually clicking ヒント1/2/3 against a real seeded bug and reading the literal model output, repeated across two tuning passes — not inferred from the prompt text. Test accounts/exams/tasks deleted afterward in every pass.

### Setting-item explanations: popup hints, not permanent caption text (convention, 2026-09-19)

Established while building 演習モード (practice mode, `Exam.mode: 'EXAM' | 'PRACTICE'` — an untimed/unlimited-retry learning-support flow alongside the timed exam flow) and its per-task AI hint feature (`Task.aiHintEnabled` / `Task.aiHintMaxStage`, staged non-revealing hints from a browser-local LLM — same `@mlc-ai/web-llm` model as "AI作問サポート" above, reused via `loadAiAssistModel()`). Both features have their own full writeups ("演習モード" and "AIヒント" above); this section only covers the UI convention that came out of authoring their settings.

**Going forward, a setting's explanation/caution text belongs in a `HelpPopover`, not a permanently-visible `<p className="text-xs text-mp-muted">` caption, whenever the content is supplementary detail rather than something every teacher must see without clicking.** Concretely:

- `src/components/HelpPopover.tsx` — a small "?" button next to a form label; click toggles a popup with the explanation, closes on outside click or `Escape` (same conventions as `ConfirmDialog`/`UserDrawer`). Usage: `<HelpPopover text="..." />` immediately after the label text, inside a `flex items-center` label so it sits on the same line.
- Keep a short always-visible caption only for facts that change what the teacher should do *before* they'd think to click "?" (e.g. "3択どちらか選んでください"-level essentials, or something the EXAM/PRACTICE branch of a conditional needs that isn't in the popover at all). Anything more detailed — mechanism explanations, edge cases, "here's what happened when we actually tested this" caveats — goes in the popover text instead.
- **Don't say the same thing in both places.** When adding a popover next to an existing caption, check whether the caption is now fully redundant with the popover text; if so, delete the caption rather than keeping both (done 2026-09-19 for the exam「モード」select and the task「AIヒントを許可する」/「公開する最大段階」fields — see `src/lib/examModeHelp.ts`'s `EXAM_MODE_HELP_TEXT`, shared between `TeacherDashboard.tsx`'s create form and `ExamDetailPage.tsx`'s edit form, and `TaskEditorPage.tsx`'s `AI_HINT_ENABLED_HELP_TEXT`/`AI_HINT_MAX_STAGE_HELP_TEXT`). If the caption said something the popover didn't, move that fact into the popover text first, then delete the caption — don't just delete and lose the fact.
- The AI-hint popovers are also where the "verified via real testing" convention (see AI作問サポート above) shows up for this feature: `AI_HINT_ENABLED_HELP_TEXT` explicitly warns that stage-3 hints can land close to a full answer on simple bugs, a finding from actually running the staged-hint prompts against a real off-by-one bug during tuning, not a hypothetical caveat.
